flua feedback — migration of EventRunner7 from plua

Report on the plua → flua migration of EventRunner7 (findings against flua 0.1.90; #1 and #2 resolved by flua 0.1.91 — noted inline; remaining items open as of 0.1.91). Covers where flua behavior cost time, where it could be more helpful, and gaps in the agent docs/skills that made things harder than they needed to be. Everything below was observed first-hand during the migration; probes were run to confirm the claims.

1. Path resolution inconsistency (fixed in 0.1.91 — half of it remains)

--%%file/--%%include now resolve relative to the file that declared them (main QA's dir for main-declared, the include file's own dir for include-declared) — fixed in flua 0.1.91. io.open/dofile inside a QA still resolve relative to the process cwd, so the two mechanisms still disagree, but the QA-file side is now sane.

What 0.1.90 forced, and what 0.1.91 changed:

  • Under 0.1.90 a QA in tests/ could not --%%file the repo-root EventRunner.inc (paths resolved against tests/). The project shipped er-load.lua — a boot-time module loader that walked up from the QA directory to find the repo root and loaded every module EventRunner.inc lists — purely to work around the resolution rule.
  • With 0.1.91, a nested test QA just declares --%%include:../EventRunner.inc and the .inc's own --%%file:src/… entries anchor to the .inc's directory. Verified: ER boots, Sim devices load, er.eval works with no loader. All 46 test files were migrated to --%%include:<depth>/EventRunner.inc and er-load.lua deleted.
  • scripts/er no longer needs its cd-to-repo-root workaround (verified running from /tmp).
  • test/_diag.lua (at test/) had a wrong-depth --%%file:../../er-load.lua from a mechanical header rewrite; only flua --check caught it (see #9). The depth trap is gone with the new scheme (each file's depth is correct relative to itself, and --check still verifies it).
  • Remaining inconsistency: io.open is still cwd-relative, so QA code that reads project files (e.g. src/Sim.lua loading tests/stdQAs/*.lua) only works when flua is started from the repo root. Suggest: set cwd to the QA file's directory so both mechanisms agree, or document that QAs with relative io.open must be run from the project root.

2. plua's --%%headers: — solved by 0.1.91's --%%include

--%%headers:EventRunner.inc (plua: inline a header file's directives into every QA) was an unknown directive in flua 0.1.90 — it warned and ignored it (verified: WARNING flua.config: unknown --%% directive). This was the single biggest structural migration issue: every one of the 28 regression QAs and all tests/*.lua suites used it, and there was no drop-in replacement.

flua 0.1.91 fixes it: --%%include:FILE is the equivalent, and its --%%file entries anchor to the include file's own directory, so --%%include:../EventRunner.inc from a nested test QA just works (nested includes anchor per level). The whole er-load.lua mechanism from #1 was deleted in favor of a one-line include. The flua-setup skill should now simply say: plua --%%headers:X → flua --%%include:X, with paths relative to the declaring file.

3. --instant breaks ER-style event engines

--instant (recommended by AGENTS.md for "timers fire immediately") collapses the whole timer heap into one pass. ER computes delays against os.time(), so this corrupts its event engine. Reproduced with a minimal probe (@@00:00:05 => log(...) plus wait(3); log(...)):

  • --speed 60: interval fires at 12:00:02, :07, :12, :17; wait(3) fires 3 s later. Correct.
  • --instant: the interval never fires in 30 simulated seconds, and wait(3) fires 27 s late at the moment the run ends (12:00:30).

This cost a full debugging detour during the migration (the runner was first converted to --instant because it looked like the fast option; the verdict only emerged from diagnosing the @@ interval behavior). The workaround is --speed 3600 --max-hours 24 in test/run-tests.sh.

Suggestion: document that --instant is only safe for QAs that never compute delays from the clock (pure setTimeout chains), and that engines using os.time()-relative logic (ER, and anything with @@/daily timers) need --speed. AGENTS.md currently recommends --instant unconditionally for timer logic — for this project that advice is actively harmful.

4. --speed runs the virtual clock continuously (drift everywhere)

plua's speedTime fast-forwarded deterministically (advance to the next timer deadline). flua's --speed N runs the virtual clock continuously at N× wall speed, so virtual time passes while your code executes:

  • ER boot takes ~30 ms wall → ~100 virtual seconds of drift at --speed 3600 before main() even runs. Host-side captures like os.time()/os.date() in a test body land ~1–2 s away from the value now/ostime() computes inside the expression — pure flakiness.
  • Tight now-relative windows (now..now, now+1..now+2) flake because each now read inside one expression can land in a different virtual second (1 virtual s = 278 µs wall at 3600×).
  • Fixes required in test/expr/time.lua (exact 12:00:00 assertions → range/ pattern assertions) and tests/eventrunner_test.lua (compare against a pinned boot epoch, ≥60 s between-windows, wait(4) → "≥ 4 s"). Two test files had to become drift-agnostic; that is mechanical but easy to miss, because the failures are intermittent (a suite can pass 2/3 runs).

Suggestion: offer a deterministic deadline-ordered fast-forward mode (plua speedTime semantics) — --speed plus "pause the clock while Lua runs" — or document the continuous-clock behavior and recommend range assertions for time-sensitive tests.

5. No auto-termination; --run-for masks hangs with exit 0

flua QAs do not terminate when the event queue drains; a test that forgets os.exit hangs forever. --run-for N caps the run but exits 0 when it kills the QA (verified: a QA that only prints "started, never exits" returned exit 0 after --run-for 3). For CI this means a hung/incomplete suite looks green unless you also grep the log for the completion line — exactly the class of false pass the migration almost shipped (--run-for capped runs of suites that never finished).

Suggestion: exit non-zero when --run-for expires, and/or emit a "run-for expired" marker in --log json so runners can detect it.

6. json.encode output differs from HC3/plua

flua's json.encode pads arrays with spaces ([2, 4, 6]); plua and the real HC3 encoder emit [2,4,6]. String-exact assertions written for plua fail under flua even though the data is identical (this was the last red test in the regression suite, test/expr/listcomp.lua). The tests now normalize whitespace before comparing — meaning the tests no longer pin the encoder format at all.

Suggestion: match the HC3 encoder's compact output (tests should run identically against flua and the real controller), or document the difference prominently.

7. What worked well (worth keeping)

  • flua --check caught the wrong-depth --%%file in test/_diag.lua with an exact "no such file" message — the static check is genuinely useful and was the safety net for the mechanical header rewrite.
  • plua-style directive warning (-- %%save, space before %%) flagged every stale plua directive in the codebase.
  • Unknown device type error listed valid alternatives ("did you mean 'com.fibaro.device'?").
  • _FLUA.loadQAfromFile/loadFQAfromFile are documented in USAGE.md and replaced plua's loadQAString/loadFQA cleanly (src/Sim.lua, tests/fqa_test.lua).
  • flua-test assertions library exists and works as AGENTS.md claims (verified with a probe). Note: the repo kept its own plua-era test/harness.lua instead; a note in the skills about "migrate an existing plua harness → keep it or switch to flua-test" would have removed the decision.
  • --nogreet, --color never, --log json made machine-readable runs easy.

8. Agent doc / skill gaps

  • AGENTS.md: "flua --api local --instant qa.lua # timers fire immediately" — harmful for ER (see #3). Needs a caveat: only for QAs without os.time()-relative delay logic.
  • AGENTS.md documents flua-test but the repo's own harness does the same job; no guidance on which to use when migrating an existing plua test harness.
  • No skill or doc covers the one costly behavior that remains: --speed continuous-clock drift (#4). The path-resolution (#1) and --%%headers: (#2) gaps are now solved by 0.1.91; the flua-setup skill should document the direct mapping (--%%headers:X → --%%include:X, declaring-file-relative paths).
  • --run-for exit semantics (#5) and json.encode spacing (#6) are undocumented traps for CI.
