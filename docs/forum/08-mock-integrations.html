Mock your integrations: HTTP, TCP, UDP and WebSocket servers in Lua

Many QAs talk to something outside the HC3: a weather API, a LAN device speaking a raw TCP protocol, a service pushing WebSocket messages. How do you test that without the external service — and without writing Python mock servers?

flua's answer: your QA can host mock servers itself. Plain Lua, no HC3 counterpart needed, four transports — HTTP, TCP, UDP, WebSocket:

local http = net.HTTPServer()
http:listen(0, function(req)                -- {method,url,headers,body}
  if req.url == "/hello" then
    return {status = 200, body = "Hello " .. req.body, headers = {["X-Mock"] = "1"}}
  end
  return {status = 404, body = "not found"}
end)

local tcp = net.TCPServer()
tcp:listen(0, function(data) return data:upper() end)   -- package in, reply out

local udp = net.UDPServer()
udp:listen(0, function(data, ip, port) return "got:" .. data end)

local ws = net.WebSocketServer()
ws:listen(0, function(message, isBinary) return "echo:" .. message end)

Then point your QA's real client code at the mock — the same code that will talk to the real service later:

net.HTTPClient():request("http://127.0.0.1:" .. http.port .. "/hello", {
  options = {method = "POST", data = "flua"},
  success = function(resp) print(resp.status, resp.data) end,   -- 200  Hello flua
})

Notes on the semantics (they are deliberately simple, one-shot request/response):

  • Handlers are ordinary closures — keep state across requests (local hits = 0), branch on req.url, call api.get. Write the mock from the service's protocol documentation.
  • listen(0) picks a free port — read server.port. server:close() stops it; servers die with their QA.
  • A handler that raises answers HTTP 500 with the error text; no reply within 10 s is a 504. The reply is the handler's synchronous return value, so a mock can't simulate latency — for timeout tests, point the client at an unreachable port.
  • Mock code can live in a sibling file loaded with require("mocklib") — and only --%%file files are packaged, so the mocks never ship to the HC3.

The example that ships with flua does exactly what this series has been building toward: it hosts all four servers and verifies its own clients against them, ending with exit(failures) — F5 it, or run it from the terminal:

flua --api local mockServer.lua     # in the directory flua --examples prints

PASS: http status (200)
PASS: http body (Hello flua)
PASS: tcp reply (HELLO)
PASS: udp reply (sender's port echoed)
PASS: ws reply (echo:hi)
failures: 0

That closes the loop: UI, timers, device logic, deployment — and now the integrations too — all developed and verified on the laptop before anything touches the controller.

Where to go from here: the repo has a tutorial (docs/tutorial/, ten chapters), a full user guide (USAGE.md), and 40+ runnable examples (flua --examples). If something does not behave like the HC3 or you are missing a feature, open an issue — flua is built to match the controller, and feedback from real QAs is what drives it.
