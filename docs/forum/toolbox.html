The flua toolbox — every --tool command

Everything flua does is a command: flua --tool <name>. The VS Code extension's buttons are these commands with a GUI on top, the MCP server exposes them to agents, and a bare flua --tool lists them all (each with --help). This post is the tour — all 24 tools, grouped by what they do, as of flua 0.1.142.

Scaffold and understand your devices

  • setup — scaffold a QA project: .vscode configs, agent files and per-file policies. The first command in a new workspace.
  • newQA — scaffold a QA from one of the 30 standard device-type templates (the type's canonical actions and properties, ready to run):
flua --tool newQA binarySwitch "Demo switch"   # -> binarySwitch.lua
  • catalog — list the 190 device types the sim supports (the --%%type catalog); --json for the machine shape.
  • typeinfo — the implementation contract of one type or interface: its properties (types, defaults, enums), the interfaces it carries, and the actions a QA should implement as QuickApp:<name> methods — each tagged with where it comes from (the type, a base type, an interface).
  • ui — print a QA's declared UI as text (elements, callbacks, options); --json for the structured payload, --device ID to fetch a real HC3 device's UI and render it back to --%%u rows.

The house and the controller

  • house — the house as one JSON document: devices (id, name, type, room), global variables, scenes, custom events. The data behind the extension's completions and the agent's ground truth.
  • hubList — the hub and its QuickApps as one JSON document (ids, names, types, rooms, modified timestamps) — what the extension's hub view renders.
  • hub — named controller profiles: add/list/switch/remove for the .env chain. list shows names, urls and serials — never passwords:
flua --tool hub add home http://192.168.1.20 admin   # prompts for the password
flua --tool hub switch home                          # repoint the global default
flua --tool hub switch home --project                # pin this project only
  • state — inspect simulator state from a seed/db file: dump, alias scan, tree check — what the simulated house will look like before you run.
  • createDB — build an offline db from the HC3 (device 1, location, panels): a snapshot to develop against without the controller.
  • icons — populate the icon cache (icons download) — the catalog of controller icons the sim serves.

Package and deploy

  • pack — package a QA project (main file + --%%file extras) into a .fqa file on disk:
flua --tool pack binarySwitch.lua          # -> Demo_switch.fqa
  • unpack — the reverse: a .fqa back into a flua project (<name>_main.lua plus one file per packaged QA file):
flua --tool unpack Demo_switch.fqa -d unpacked   # -> unpacked/Demo_switch_main.lua
  • uploadQA — package an unpacked project and upload it (new QA, or the id in a downloaded <Name>_main_<id>.lua).
  • updateQA — update an existing QA on the HC3 from an unpacked project (all files at once).
  • uploadFile — push one QA file (reads --%%deviceId/--%%qaFile from the file).
  • uploadFQA — upload a .fqa package as a NEW QuickApp.
  • downloadQA — download a QA from the HC3 and unpack it into individual Lua files (the start of the edit → test → update loop).
  • downloadFQA — the same download as a .fqa file.
  • installHelper — deploy the FluaHelper QA to the HC3 and point it at this machine (the controller-local API bridge).

Inspect and diagnose

  • migrate — scan a project for plua leftovers and migration hazards (the checklist when a QA moves from the old tooling).
  • ws — probe a WebSocket endpoint: handshake, send frames, soak with pings — debugging socket QAs without a second tool.
  • parityCapture / parityCleanup — capture REST shape fixtures from a real HC3 for offline parity replay, and list/remove the flua_p_* artifacts afterwards.

Two commands cover the rest of the surface: a bare flua --tool lists every tool with its one-line purpose, and flua --tool <name> --help gives the tool's own usage. Agents get the same tools through flua-mcp's flua_tool, so anything this page shows is something an agent can run.
