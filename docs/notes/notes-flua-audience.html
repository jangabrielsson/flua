Widening the flua audience — plan

Drafted 2026-11-15 with Jan. flua's uptake today is the ex-plua hard core; the goal is to lower the entry for the non-programmer majority of the Fibaro forum. This note records the strategy and the builder design.

The barrier, decomposed

Today a new user clears: install Python → pip → install flua → get an editor (VS Code) → write a Lua file → run it → move the QA to the HC3. The agent path adds three more steps (install, configure, pay). Each step filters people out; flua currently serves only those who would have cleared all of them anyway.

Strategy — four plays, in sequence

  1. Consume first (posting discipline, zero product work). A forum member can download a finished .fqa and upload it in the HC3 web UI — no flua, no Lua. They are using flua's output without knowing it. The funnel: consume a finished QA → want one line changed → "flua makes that change safe" → install. Ship finished QAs as downloads with a marked "EDIT THESE 3 LINES" header.
  2. Recipe library (content, feeds 3). 10–15 scenarios ("light on at sunset", "notify when the door opens"), each a complete QA with three marked lines to edit. Same artifacts serve the forum and the builder.
  3. The QA builder (the product bet). A browser page on flua's own local server (the proven viewer/icon-manager pattern): pick a recipe → pick your actual devices/rooms/scenes from dropdowns fed by the live HC3 → tweak values → flua generates the QA → "try it in the simulator" → upload. A non-programmer never sees Lua, never opens an editor.
  4. One-click install (distribution, later). A single executable (PyInstaller-style; macOS app + Windows exe) removes Python and pip entirely. After the builder exists, since the builder is what they open. Needs CI builds and code signing for the Gatekeeper experience.

The agent angle slots in at the top of the funnel (custom logic), not as the entry point.

The builder's recipe library lives on GitHub — no releases needed

The recipe set must grow without shipping a new flua. Recipes therefore live in the flua repo and the builder fetches them from the same GitHub that already serves examples/iconInstall.lua's icons (raw.githubusercontent.com/jangabrielsson/flua/main/...):

  • recipes/ in the repo — one folder per recipe: manifest.json + main.lua (+ icons when a recipe ships a custom icon set). The manifest is the builder's contract and the forum post's "what to edit":

json { "id": "light-at-sunset", "title": "Turn a light on at sunset", "description": "One sentence for the picker.", "params": [ {"name": "deviceId", "label": "Light", "kind": "device", "filter": "com.fibaro.binarySwitch", "default": 0}, {"name": "offset", "label": "Minutes before sunset", "kind": "number", "default": -30} ] }

kind drives the UI: device/room/scene become dropdowns populated from the live HC3 (?isTypeOf=/type filters for devices), number/ text/boolean become inputs. The template QA carries the params as --%%var:name=<default> lines — the generator bakes the picked values into the header (--%%var:deviceId=123), so the same file is the human-editable "finished QA" from play 1 and the builder's template. - recipes/index.json (checked in, regenerated by a script) lists the manifests — the builder fetches the index first, then a recipe's files on selection. Cached under ~/.flua/recipes with a refresh action; the wheel ships a snapshot of the index as the offline fallback. - Trust = the repo. Recipes come from the flua repo the user already trusts (the wheel's source); the builder never executes fetched content outside the sim, and the fetched QA is a plain file the user can read. - New recipe = one merge. No release, no packaging — the index entry appears on the next builder refresh.

Open questions (decide when building 3)

  • Upload step: uploadQA directly, or offer a .fqa download too (the consume-first artifact)?
  • Builder entry point: flua --tool build (new tool) or a tab in the existing viewer page?
  • Recipe params beyond the flat kinds (e.g. time-of-day pickers, lists)?
  • Offline behavior: the shipped index snapshot, with a banner when the GitHub fetch fails.

Milestones

  1. Posting discipline + the first 5 recipes as forum downloads (no code).
  2. recipes/ layout + index.json + the builder page (fetch → pick → generate → simulate → upload), starting with the 5 recipes. Shipped as the MVP: flua --tool build serves the builder page — recipe list from the index (GitHub refresh + shipped fallback), HC3-fed pickers with typed-id fallback, param baking into the marked --%%var lines, a .lua download, direct upload to the HC3 (import endpoint), and simulate-in-place: the generated QA runs on the laptop with a virtual clock, picked devices re-pointed at bundled sim devices. Parked as a PoC (2026-11-15) — waiting for forum feedback before more investment; ADR 0015 delimits it against the no-wizard decision.
  3. One-click installers (macOS/Windows) once the builder is worth opening.
