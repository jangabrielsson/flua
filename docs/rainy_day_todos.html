Network policy — deny/loopback gate (Change 04, simplified)

  • What: an opt-in --network-policy deny|loopback (and a --no-user-config for inherited credential/config discovery) applied at flua's transport boundary — HTTP/WebSocket/TCP/UDP. Deny before connect.
  • What NOT to build: the full proposal's allowlists, DNS-resolution checks, redirect rules, IPv4/IPv6 parity. A wrong network policy sells false confidence, and it is accident-prevention, not a security sandbox (a hostile QA runs in-process).
  • Rationale: real value for running foreign/untrusted QAs (the pt report ships its own audit-hook wrapper for exactly this); the 80% version covers the accident risk.
  • Pinning test: loopback fixture works; external target fails before connect; background retries respect the policy; no live devices.

Resource summary (Change 09, the small half)

  • What: --resource-summary — pending timers, owned HTTP requests, subscriptions, queue lengths, before/after stop or restart. Leak and lifecycle debugging.

Pump wake-up, event-driven (parked 2026-11-03)

  • What: replace the pump's idle polling entirely — an asyncio.Event set by enqueue_outbound (with call_soon_threadsafe from the worker threads) so the pump sleeps until there is actual work.
  • What NOT to touch blindly: the get_nowait() drain loop exists because wait_for(queue.get(), timeout) lost messages on Python <= 3.12 (ADR 0006, CI failures) — an event wake-up must keep the drain semantics and earn trust on the full 3.11-3.15 CI matrix.
  • Rationale: shipped the cheap 80% first (the adaptive idle poll: _PUMP_POLL_IDLE when no timers are pending); the event-driven version removes the remaining ~20 wakeups/sec but rewrites the most delicate part of the engine.

QA id band — HC3 devices approaching 5000 (parked 2026-11-03)

  • What: the real HC3's QA ids never get reused, and one user's controller is already at 4357 — once real device ids cross 5000 they collide with flua's emulated QA ids (engine-assigned from 5000). The fix, in order of leverage: 1. Cheap insurance: in online/hybrid mode the allocator consults the real HC3's /devices id set when skipping (today it only skips ids in the sim's own state) — collision becomes impossible without any configurability. 2. Shape-based QA detection: api/state.py:is_plugin_device() uses id >= 5000; replace with device-shape markers (quickAppVariables / view / uiView), which also makes everything base-agnostic. 3. Configurable base: a qaIdBase knob (.flua.lua / CLI flag) for users who want a clean id band — the seed point is a single line (engine.py:_next_qa_id).
  • What NOT to worry about: the blast radius is small — one seed point, one id-range heuristic, the online allocation gap; tests keep the default base and stay green.
  • Rationale: parked at the owner's request ("we can wait a bit longer until we go there"); items 1-2 are worthwhile insurance before any configurability.

Parked 2026-11-12, from the custom-icon work (User sets, uploadExternalIconSet):

QA self-installs its own icon set (idempotent, no stored state)

  • What: an example QA + quickapp-patterns skill section for "ensure my icon set exists": on init, api.get("/icons") -> filter deviceType == self.type and iconSetName starting with User; fetch each candidate's state file via net.HTTPClient from http://127.0.0.1/assets/userIcons/devices/<set>/<set><state>.png and byte-compare with the bundled icon; match -> already installed -> updateProperty("deviceIcon", id); no match -> uploadExternalIconSet -> new id. Replaces the quickVar/internalStorage "already downloaded?" bookkeeping that went stale on QA reinstall (duplicate sets, lost ids).
  • Ground truth (live-verified 5.22x): the HC3 serves uploaded icon files byte-identical (md5-equal) under /assets/userIcons/devices/; the fibaro tree is placeholder art for User sets; binary/multilevel sets have no base file, only state files; the named shutter states serve under the same <set><state>.png naming (live-verified with a baseShutter set, id 1111); custom ROOM/SCENE icons serve FLAT — /assets/userIcons/rooms/<iconName>.<ext> and /assets/userIcons/scenes/<iconName>.<ext>, no <set>/ directory (live-verified: room id 1001, scene id 1001 — each category has its own id sequence); icons must be >= ~128x128 (INVALID_ICON_SIZE otherwise); POST /api/icons multipart contract: type=device, deviceTemplate=<type>, file fields per the provider (icon/icon0+icon100/icon0..100/iconOpening...), response 201 {"id":N,"iconSetName":"User<N>","fileExtension":"png"}. DELETE contract (mined from the web UI's Angular bundle + live-verified): DELETE /api/icons?type=<device|room|scene>&id=N&name=<set>&fileExtension=<ext> — type is the icon CATEGORY (not deviceType; WRONG_TYPE otherwise), id is required (MISSING_PARAMETER); 200 + empty body on success. POSTs to unknown /api/icons/* paths HANG the connection — never guess there. (flua --tool icons ui — the icon manager — builds on all of this.)
  • The 11111/11112 split (probed from a QA on the controller, settled): through api.get("/proxy?url=http://localhost:PORT/<path>"), 11112 is the full local API — JSON bodies that api.get decodes into Lua tables (synchronous + credential-free recipe for GETs). 11111 answers 200 with non-JSON bodies for such GETs (nil, 200 after the decode step); its one established use is Fibaro's own uploadIconFiles (POST http://127.0.0.1:11111/api/icons). Neither port serves the asset tree — net.HTTPClient to 127.0.0.1:11112/assets/... 404s ("The requested method does not exist"), 11111 501s. The real icon source is the plain web server: http://<hc3>/assets/userIcons/devices/... on port 80, served by nginx credential-free (verified both from a QA on the controller and externally) — that is the canonical icon-fetch recipe, and flua online rewrites 127.0.0.1 to the controller keeping port 80 with no auth.
  • flua emulation divergences found along the way: (1) FIXED — net.HTTPClient and the /proxy fetcher corrupted binary bodies (the utf-8-replace decode inflated a 2442B PNG to 4829B of mojibake): responses now travel as raw bytes (lupa carries them into Lua strings unchanged; a str channel cannot be byte-faithful — even latin-1 doubles up at the bridge). Pinned by binary /blob tests. (2) flua rewrites 11111 and 11112 identically to the standard API — faithful for 11112, too lenient for 11111 GETs (the controller answers non-JSON there). (3) api.get("/proxy?...") of a binary body returns the raw bytes where the HC3 nils it — kept as a deliberate flua extension (the bytes are what recipes need); document it. (4) flua's /proxy route ignores the HC3's username/password query parameters (Fibaro's own getProxyUri(uri, login, password) helper — the undocumented target-auth surface; no user code seen using it yet). Fix when needed: prepend them as userinfo in proxy_get so fetch_url's existing userinfo→Basic path applies; pin with a mock-server test.
  • Flua angle: recipe is online-only (needs /api/icons + the 11111 loopback; the sim has the catalog route but no asset tree — degrade gracefully). Testable against the mock HC3. Related parked options from the same session: a _FLUA.saveIcon(set, file, bytes) bridge call and lazy fetch+cache in the icon channel (online/proxy) so the viewer warms the cache on demand — both "wait for now".
