flua — user guide for QA developers

flua runs Fibaro QuickApps offline on your Mac or PC. You write the same Lua you'd write on the HC3 — QuickApp, fibaro, api, net, mqtt — and flua provides the rest of the world: a simulated HC3, real network access, a virtual clock, a proper debugger with breakpoints, and a one-command path back to the HC3 as a .fqa file.

The HC3 editor is tiny and debugging there means print() statements. flua exists so you can develop in your real editor, with real tooling, and upload when it works.

flua aims at two kinds of development: agent loops (an agent runs the QA, reads PASS/FAIL, iterates — served by flua-mcp, structured logs, and the bundled skills) and programmers who want their standard toolset — VS Code, git, a debugger, tests. flua itself stays the engine; wizards and GUI conveniences are built as apps on top of it, and the VS Code extension is the first. Every app feature is a CLI or --tool command first, so agents and scripts get the same surface as the GUI.

Install

Python 3.11+. lupa (which bundles Lua) is the only runtime dependency. The full runtime matrix — tested Python versions, the Lua 5.4/lupa pin and why, and the HC3's own Lua 5.3 — is in docs/compatibility.md; flua --version --machine prints the installed versions as one JSON line.

pip install fibaro-flua        # from PyPI — installs the flua command

The PyPI page carries this guide in full. The wheel also ships the examples/ QuickApps — find where they are installed with:

flua --examples               # prints the directory; copy the examples out
flua --api local $(flua --examples)/timers.lua   # ...or run one in place

From a checkout (development):

cd flua
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
flua --version

flua --version --machine prints one JSON line instead ({"version", "lua", "lupa", "python", "integerBytes", "locale", "ctype"}) — the stable capability probe for agents, installers, and scripts. locale is your environment; ctype is the effective character-classification locale the engine forced (C.UTF-8, falling back to C) before the Lua runtime exists — Lua's pattern classes %s/%a/%d are libc ctype lookups, and on Polish/Windows locales %S+ splits multibyte characters mid-byte (the plua 1.2.79 fix). Known platform limit: macOS's C.UTF-8 still classifies high bytes as %a; Linux/Windows get strict-ASCII classes. The wider probe is flua --capabilities-json: runtime metadata plus the compatibility surface table (implemented/partial/unsupported per category — QA methods, net.*, the REST sim, runtime modes, tooling).

Your first QuickApp

A QuickApp is an ordinary Lua file. QuickApp:onInit runs exactly like on the HC3, and self:debug prints immediately (unlike the HC3, where you'd only see it in the debug window):

--%%name:hello
-- --------------- EOH ---------------
function QuickApp:onInit()
  self:debug("I started")
  setTimeout(function() self:debug("one second later") end, 1000)
end

Save it as hello.lua and run it:

.venv/bin/flua hello.lua

Every .lua file you pass is a QuickApp — it gets QuickApp, fibaro, api, net, mqtt, timers, and runs onInit exactly like on the HC3. Anything that has nothing left to do (no timers, no network connections) makes flua exit; QAs with timers or open connections keep running.

Running QAs

.venv/bin/flua script.lua              # one QA
.venv/bin/flua qa1.lua qa2.lua         # several QAs, isolated, can talk to each other
.venv/bin/flua -e 'setTimeout(function() print("hi") end, 100)'
.venv/bin/flua --run-for 5 script.lua  # at least 5 virtual s, then exit when idle —
                                        # but never past 5 WALL s (a hard deadline:
                                        # an open SSE stream or keep-alive QA can't
                                        # keep the run alive past it — and when the
                                        # deadline cuts work short, exit 1)
.venv/bin/flua --run-for -3 script.lua # exactly 3 virtual s (step mode: run
                                        # until idle, at most 3 wall s — the
                                        # deadline jumps fire regardless of 3)
.venv/bin/flua -D mode:online -D var:x=42 script.lua
                                        # inject directives as if appended to
                                        # the QA's header — test foreign code
                                        # without editing it (repeatable; the
                                        # injected lines win over the file's)
.venv/bin/flua --strict-tests script.lua
                                        # CI mode: an unhandled callback error
                                        # (timer/UI/net) fails the run with exit
                                        # 1 — sticky: a later callback's
                                        # _FLUA.exit(0) cannot clear it
.venv/bin/flua --result-json result.json script.lua
                                        # one machine-readable final record
                                        # (schemaVersion, status passed/failed/
                                        # timeout, exitCode, runtime, clockMode,
                                        # wall/virtual seconds, failures) —
                                        # written atomically; a missing file
                                        # after a kill is incomplete, never a pass

.flua-directives, a file in the main QA's directory, is the file-based spelling of -D — same --%% syntax, discovered automatically (see below), so a VS Code F5 run picks it up with no launch.json edits. Precedence: the QA's header < its --%%include defaults < .flua-directives < -D flags.

Virtual time — great for testing long-running logic (--run-for counts virtual seconds: --instant --run-for -5 runs five simulated seconds, and an interval firing once per simulated second fires exactly five times):

.venv/bin/flua --speed 60 script.lua    # 60x faster
.venv/bin/flua --instant script.lua     # deadline-ordered fast-forward: the clock jumps
                                        # to each timer's deadline before its callback runs,
                                        # one at a time — instant AND os.time()-coherent
.venv/bin/flua --step script.lua        # the same deadline-ordered fast-forward under
                                        # its plua speedTime name

--instant and --step are the same discipline: each callback observes its own deadline in os.time()/os.date(), timers a callback schedules are ordered against the queue, and days of simulated time complete in seconds. (--instant used to collapse the whole timer heap into one pass — a 1 s callback observed 2 s when a 2 s timer was also queued; that is fixed.) Event engines with @@-rules/daily timers and any os.time()-relative scheduling work under both; --speed is the continuous clock — virtual time also passes while your code executes (a slow boot becomes virtual time at high speeds), so time-sensitive tests should assert ranges or pin deadlines with --instant/--step. Engines with a perpetual housekeeping loop (EventRunner's midnight scheduler) should tag it _FLUA.background(fn): tagged timers still fire while the run lives but never keep it alive, so --step --run-for -N exits 0 the moment the real rules drain instead of riding the wall cap.

fibaro.sleep(ms) suspends the calling QA for ms of virtual time — other QAs keep running, and the sleep follows --speed/--instant like a timer. Messages destined for the QA while it sleeps (timer callbacks, actions, UI and network events) are queued and delivered, in arrival order, after the sleeping callback resumes. It works anywhere in QA code — top level, onInit, callbacks — because the QA identity is registered before the file executes; only outside a QA (main-state code) does it raise an error.

VS Code setup

The repo ships .vscode/launch.json with five configurations (the --tool setup template has the same five, with the debug interpreter resolved to flua's absolute path — VS Code doesn't inherit the shell's PATH on macOS, so a bare flua would not be found; the run configurations use the selected Python interpreter), all running with --api local — the offline playground):

  • Flua: Run Current File — runs the file in the panel.
  • Flua: Run Current File (Terminal) — runs it in the integrated terminal (pick this one for self:debug output you can scroll).
  • Flua: Run Current File (UI) — runs it and serves the UI viewer at http://127.0.0.1:8090/ (if 8090 is busy the server picks the next free port — open the printed URL).
  • Flua: Debug Current File (mobdebug) — real debugging: breakpoints, stepping, variable inspection. Install the VS Code extension Lua MobDebug (alexeymelnichuk.lua-mobdebug), open your QA, press F5 with the mobdebug configuration selected. It uses the project venv's flua executable on macOS and flua.exe on Windows. flua waits for the debugger before running your code.
  • Flua: Debug Current File (UI+mobdebug) — the same, plus the UI viewer server (--ui 8090): debug your QA while its UI is rendered at http://127.0.0.1:8090/.

While you step through code, print/self:debug output appears immediately — logs never queue behind a paused program.

The flua CLI writes stdout and stderr as UTF-8 on all platforms, including when a debugger captures output through pipes on Windows. This preserves Unicode text and the startup rocket in VS Code's debug console.

Lua Language Server support: the repo's .luarc.json declares Lua 5.4 with the HC3 globals and loads the bundled .luals/ type library — LuaLS definitions for QuickApp, fibaro, api and json — so QA code in the repo gets autocomplete and parameter hints. flua --tool setup ships the same configuration (and the type library) into scaffolded projects for pip users; the two copies are kept byte-identical by a test. Setup also writes .vscode/flua.code-snippets — shortcut snippets for the common QA patterns (qa-header, qa-http, qa-rs, qa-btn/qa-slider/qa-switch/ qa-select, qa-simdevice, qa-selfassert): type the prefix in a .lua file and accept the completion. The file is managed — upgrades deliver new snippets until you edit it, then it's yours.

The flua VS Code extension

The repo also ships the flua VS Code extension (vscode/) — the explorer drives flua without touching launch.json:

  • Right-click a file → flua: pack a QA into a .fqa, unpack a .fqa into a project, upload a file / a new QA / an updated QA to the HC3, download a QA, scaffold a QA from the 30 type templates, or run --tool setup.
  • Check on save: saving a .lua file runs flua --check --json; syntax errors, unknown --%% directives, plua-style directive typos, and deprecated REST endpoints appear in the Problems panel (findings for --%%file includes land on those files).
  • .fqa packages open in the flua QA editor: the package summary (name, type, interfaces) plus the packed metadata (properties like manufacturer/userDescription, quickAppVariables one per line, and a collapsed UI summary) and a Lua preview per file with Unpack/Upload buttons; the raw JSON stays available via "Reopen Editor With… Text Editor" (validated against flua's package schema).

The extension only shells out to the flua executable — auto-detected from a workspace .venv, else flua on PATH, else the flua.executable setting. Tools run in the shared flua terminal so interactive HC3 credential prompts work. Install it from the VS Code marketplace as GsonSoft-development.flua (its version tracks the flua release — release.sh bumps package.json alongside the Python version, and --tool setup recommends it in the generated extensions.json). Releases publish it automatically: the Publish VS Code Extension workflow fires on every GitHub release and publishes with an organization-scoped marketplace PAT from the VSCE_PAT repo secret (global PATs retire in January 2027; the Entra ID credential flow is the planned successor). The extension also registers the flua-mcp server with Copilot on demand (the workspace's .vscode/mcp.json, venv interpreter — the same entry docs/mcp.md documents). Build it from source with npm install && npm run compile in vscode/.

The fastest loop for tinkering:

.venv/bin/flua --watch script.lua

flua restarts the QA whenever you save the file (or any --%%file file). A boot error in the saved file (syntax error, a bad --%%var, an onInit crash) is logged and that QA is left dead — flua itself stays up, and the next save with fixed code restarts the QA. Ctrl-C stops it. Works on top of the debugger too.

Without the repo (pip install)

Installed from PyPI you don't have this checkout's developer setup — the VS Code run/debug configs, the Lua Language Server settings, and the agent files (Copilot skills/instructions, AGENTS.md). One command scaffolds a QA project directory with all of it:

flua --tool setup              # the current directory
flua --tool setup my-project/  # a project directory (created if missing)

It writes .vscode/launch.json (run in the panel, run in the terminal, mobdebug, and mobdebug with the UI viewer), .vscode/extensions.json (VS Code will offer to install the Python, Lua MobDebug, Lua Language Server and Markdown Preview Mermaid extensions — the last one renders the diagrams in docs/tutorial/), .luarc.json (Lua 5.4 + the HC3 globals, with the bundled .luals/ type library — LuaLS definitions for QuickApp, fibaro, api and json, so QA code gets autocomplete and parameter hints), AGENTS.md and the .github/ skills, instructions and prompts. Existing files are kept; --force overwrites.

QA directives (--%%)

Directives are ordinary Lua comments at the top of the file. flua parses them before running; the HC3 ignores them — the same file runs in both places. Parsing stops at the end-of-header marker:

--%%name:my-qa
-- --------------- EOH ---------------
-- nothing below this line is parsed as a directive
Directive Meaning
--%%name:x the device/QA name (_FLUA.config.name)
--%%type:com.fibaro.binarySwitch device type (defaults to binarySwitch; the device structure comes from the distilled type schema — typed properties at their defaults, the type's interfaces expanded — with the catalog capture and the hierarchy as fallbacks; only types the hierarchy never heard of are an error)
--%%interface:autoTurnOff,light interfaces the QA's device gets: their properties join at their defaults and their actions join the device's action surface (comma-separated, repeatable; same semantics as POST /plugins/interfaces)
--%%properties:value=false default device properties (plural form)
--%%property:value=true raw property, scalar values; repeatable, merges
--%%var:name=expr initializes a QuickApp variable; expr is a Lua expression — 'text', 42, {a=1}, config.color, os.getenv("X") (one per line). An optional quoted string after a top-level comma is the package value distribution packages get: --%%var:name=expr,"<placeholder>"
--%%clobber:name=value Plua-compatible spelling of the package value (replaces --%%var:name's value in distribution packages)
--%%svar:name=expr initializes a secret QuickApp variable: same expression semantics and package-value slot as --%%var, but the device entry is typed password, so the HC3's web quickvar editor masks the value (*****) — getVariable and the API still return the real value. A --%%svar wins over a same-named --%%var
--%%uid:... sets quickAppUuid
--%%description:... sets userDescription
--%%model:... sets model
--%%build:7 sets buildNumber (a number)
--%%manufacturer:... sets manufacturer
--%%file:lib.lua,lib extra QA file, loads before main (see below)
--%%icons:icons/ LOCAL icon set folder previewed in the web view (see the icons section)
--%%speed:60 virtual time speed (global)
--%%step:true step mode (global): deadline-ordered fast-forward, os.time()-coherent
--%%instant:true instant mode (global)
--%%maxhours:48 stop after 48 virtual hours (global); timers beyond the horizon never fire and never keep the run alive — the run drains exactly at the limit
--%%time:speed=2,step=true,instant=true,hours=48,start=2027/10/6 12:00:20 combined runtime settings (global)
--%%time:2027/10/6 12:00:20 bare form: set the virtual start time
--%%u:{label="lbl",text="Status"} one UI row (see below); repeatable, order kept
--%%useUiView:true render the new uiView format instead of the legacy viewLayout (default false)
--%%mode:offline pin this QA to the simulated HC3 (see below)
--%%mode:online force this QA online against the real HC3
--%%mode:proxy proxy mode: mirror this QA onto the HC3 (online only, see below)
--%%mode:proxy,noUI proxy mode, but leave the proxy's UI untouched (you edit it in the HC3's UI editor)
--%%mode:readonly online for reads, never for writes: a mutating api.* call that would reach the HC3 is refused with 403 (sim-owned writes still work — they never touch the controller)
--%%mode:readonly+call the same, plus device actions pass through (POST /devices/{id}/action/..., the fibaro.call channel — test code flips a light to see it work); creating or deleting resources stays blocked
--%%debug:refreshState=true,api=true,http=true debug logging: refreshStates events / api.* calls / net.HTTPClient requests (global)
--%%debug:ws=true debug logging: byte-level net.WebSocketClient traffic — handshake leftovers, per-frame rx/tx with masked previews, close codes (global)
--%%debug:true shorthand for all three debug channels (:false disables them)
--%%loglength:120 debug line length cap (default 120)
--%%warn:true extra runtime warnings for things the HC3 stays silent about: the status channel (api error codes, off by default); the stubApi channel (shape-only stub calls, on by default, --%%warn:stubApi=false to silence); the propertyType channel (updateProperty values that do not fit the schema's declared type/enum, on by default — the real HC3 silently ignores the update) (global)
--%%trace:api,ui the --trace categories (api, ui, net, timer, all) as a directive (global)
--%%syslog:run.json the --syslog file — one JSON line per system/trace event (global)
--%%strict-tests:true the --strict-tests CI mode as a directive (global): unhandled callback errors fail the run with exit 1, sticky
--%%db:house.json seed the simulated HC3 from a JSON file (devices, rooms, scenes, globalVariables, alarms, profiles)
--%%replay:house.json replay a recorded house session (flua record): seeds the sim with its devices and fires its refreshState events on the virtual timeline
--%%db:+house.json seed and persist emulator state back to the file (see below)
--%%location:latitude=59.33,longitude=18.07 pin the sim's location (device 1's sunrise/sunset) — deterministic sun times without touching .flua.lua

The legacy --%%offline:true and --%%proxy:true still work as aliases for --%%mode:offline and --%%mode:proxy (an explicit --%%mode wins when both appear). --%%mode:readonly is the safety posture for exploring the live HC3: reads behave exactly like online mode, and any mutating verb (POST/PUT/DELETE) that would reach the controller is refused with 403 — writes the sim owns stay local. Without a configured HC3 it degrades to plain offline. --%%mode:readonly+call unlocks exactly one more channel: device actions (fibaro.call) pass through, so test code can flip a light on and off — creating or deleting resources stays blocked.

The emulator database (--%%db)

--%%db:house.json seeds the simulated HC3 from a JSON file — the same schema as examples/house.json and the --seed flag (the directive wins over --seed). --%%db:+house.json additionally persists emulator state back to the file as it changes (atomic writes; the file must exist — echo '{}' > db.json creates an empty one). What is persisted depends on the mode, following each mode's source of truth:

  • offline — the file is the house: devices, rooms, scenes, globalVariables, alarms and profiles, plus each QA's state (properties and quickAppVariables) and children, under a qaState section keyed by QA name.
  • online — the real HC3 owns the house data; only the emulator's own artifacts are written back: qaState and globalVariables.
  • proxy — everything worth keeping is already on the HC3; the + is ignored with a warning (seed still applies).

Seeded physical devices (no QA behind them) react to the canonical light actions: POST /devices/{id}/action/turnOn|turnOff|setValue updates their value like a real device (dimmers use 0/99 levels, "on"/"off" strings work), gated by the catalog's light interface — sensors stay inert. QAs and proxy devices are untouched. Giving seeded devices real QA logic is the layer-2 design in docs/notes/notes-device-emulation.md.

Running QAs are never persisted as devices — they are rebuilt from code each run. Children survive restarts and re-register under their parent QA, so a QA's usual api.get("/devices?parentId="..self.id) startup check finds them. QA state is keyed by QA name (not the per-run id), so persisted state is stable across runs; --%%var and the other property directives win over persisted values. internalStorage (self:internalStorageSet/Get) is persisted with the QA's state too — plugin variables survive runs like on the HC3. Variable names must match [A-Za-z][A-Za-z0-9_]* (letters, then letters/digits/underscores) — the HC3 rejects anything else with 400, and flua does the same so a QA breaks during development instead of on the controller.

Names: --%%name:value for scalars, --%%name:sub1=val1,sub2=val2 for subparameters. A typo'd directive is reported at runtime (a unknown --%% directive warning) and flua --check flags it too.

Record & replay the real house

flua record captures a real house session — the HC3's device snapshot plus its refreshStates feed — into one JSON file; --replay plays it back into the offline sim, so a QA is regression-tested against what actually happened at home:

.venv/bin/flua record -o house.json --duration 60   # capture (needs HC3 credentials)
.venv/bin/flua --replay house.json qa.lua           # or --%%replay:house.json in the header

The recording seeds the sim with the captured devices and fires each recorded DevicePropertyUpdatedEvent on the virtual timeline — QAs subscribed with RefreshStateSubscriber react exactly as they would have live, and --speed/--instant fast-forward the whole session. Recording polls /refreshStates every --interval seconds (default 1) and stores relative timestamps, so the replay is deterministic; events for devices the replay run did not seed are skipped silently. The recording doubles as a seed file: --seed house.json loads the devices without the events.

flua audit

How much of the HC3 surface does the sim cover? One command answers:

.venv/bin/flua audit            # routes + device catalog, human-readable
.venv/bin/flua audit --json     # the same numbers for agents/CI

It classifies every endpoint in docs/specs/hc3-api.json (the distilled swagger) as simulated or forwarded-online, and reports which catalog types the sim gives light-like behavior to — including the gap list: types that declare light actions but lack the light interface, so the sim never emulates them. It also reports the offline type hierarchy (devices/hierarchy.json, distilled from the HC3's undocumented /api/devices/hierarchy): how many types it knows and how many resolve to a cataloged ancestor — the fallback that keeps device types newer than the catalog capture running offline. It also checks the QA templates (quickapp-types): every template's --%%type must resolve, or --tool newQA/running the QA fails — the report lists the unresolvable ones for remapping to a parent type. The coverage floors are pinned by a test: routes, device models, the hierarchy, and the templates can only go up.

Inspecting simulator state (flua --tool state)

Agents (and humans) debugging flua itself sometimes need to look at the sim's raw state — and to answer "where did this object get stored twice?" (the shape of the updateView aliasing bug):

.venv/bin/flua --tool state --db house.json            # compact dump: devices + plugin variables
.venv/bin/flua --tool state --db house.json --aliases  # every object reachable from 2+ paths
.venv/bin/flua --tool state --db house.json --verify-tree
# exit 0 = the state is a clean JSON tree (no shared references, no cycles)

--db accepts any seed-shaped JSON — a --tool createDB output, a recording, a --%%db file. A JSON file cannot express aliasing, so the scanner's real home is a live state; the same functions are importable:

from flua.tools.state_tool import scan_tree
print(scan_tree(engine.api.state))   # {"aliases": [{"paths": [...]}], "cycles": [...]}

The house and the hub as data (--tool house, --tool hubList)

Two data tools feed the VS Code extension (the HC3 hub tree and the hub-aware completions) and give agents/scripts the same JSON:

flua --tool hubList                 # hub info + the hub's QuickApps (ids, names, types, rooms)
flua --tool house                   # devices/globals/scenes/customEvents — from the hub
flua --tool house --db house.json   # ...or from a seed/db file (the simulated house)

hubList needs HC3 credentials (the .env chain) and prints {"hub": {...}, "qas": [...]} — QAs keyed by id, rooms resolved by name, and each QA's modified timestamp (the extension cache's freshness signal). house resolves the same priority the extension needs: HC3 credentials first, else --db, else an honest empty house (a QA-only run has none). Both print one JSON document on stdout; the shape is the contract the extension and MCP clients consume.

Switching controllers (--tool hub)

Several HC3s? Give each a named profile and switch the .env chain with one command (design: docs/notes/notes-hub-profiles.md):

flua --tool hub add home http://192.168.1.20 admin   # prompts for the password
flua --tool hub list --json                           # names/urls/serials, never passwords
flua --tool hub switch home                           # ~/.env — the global default
flua --tool hub switch home --project                 # this project's .env — a per-folder pin
flua --tool hub remove home

Profiles live in ~/.flua/hubs.json (mode 0600). The chain's precedence still applies — a project pin beats the global default — and list marks the profile currently matching the chain (active, and * in the human form). Non-interactive contexts can feed add via the FLUA_HUB_PASSWORD environment variable.

And a route can be replayed in isolation — the handlers are pure functions over SimState:

from flua.api.state import SimState
from flua.api.request import ApiRequest
from flua.api.routes.plugins import plugin_update_view

state = SimState({"devices": [...]})
req = ApiRequest(segments=[], query={}, body={
    "deviceId": 10, "componentName": "btn", "propertyName": "text",
    "newValue": "on",
})
print(plugin_update_view(state, req))   # (None, 204)

Bridge errors

When a Python↔Lua conversion fails inside the API bridge (a lost reference and friends), the QA sees one opaque line. --%%debug:bridge=true turns it into a diagnosis kit: the full Python traceback in the log, the offending payload dumped to /tmp/flua-bridge-fail-<ts>-<pid>.json (a .pkl fallback for cycles/non-plain data — the log names the file), and a structured bridge_error event in /flua/systemLog (the agent feed: the timeline and flua-mcp read it). The exception still propagates, so QA behavior is unchanged.

lupa error likely cause flua invariant
lost reference a payload that shared one object across two paths (aliasing), a cycle, or a lapsed lupa object crossed the bridge engine state and bridge data are JSON trees; no lupa proxies in engine data (_fresh_copy + _plain_key/_plain_value in bindings.py)
cannot mix objects from different Lua runtimes an object passed between runtimes one runtime per QA
TypeError: cannot convert … a non-plain type reached table_from lua_to_python output is plain JSON types (unconvertible values become nil, Lua-object keys are dropped)

Debug logging

--%%debug:refreshState=true,api=true,http=true turns on per-category debug logging (any subset; it is a global directive, so an --%%include'd file can carry it). --%%debug:true is shorthand for all channels on:

  • refreshState=true logs every refreshStates event flua sees in a short form — the event type plus the id/deviceId/name/property/value/ newValue data fields that are present;
  • api=true logs the QA's api.* and api.hc3.* calls as api GET /devices/...;
  • http=true logs user net.HTTPClient requests — not the api.* calls;
  • ws=true logs user net.WebSocketClient traffic at the byte level: the handshake outcome with any frame bytes buffered from the connect response (buffered N bytes after connect — the signal for servers that send their first frame with the 101), one rx/tx line per frame (opcode, size, a short preview), close codes and reasons, and disconnects. Credential-ish values (auth, token, password, ...) are masked in the previews. With several connections open each line is labeled with its connection and host — ws[c3 192.168.50.223] tx binary 2059b … (c3 = the QA's third socket). The same stream exists structured for agents: --log json / the timeline carry net trace events (wsConnect with url/ok/error, wsEvent with event/binary/bytes).

The ws channel (and any other) can be turned on from the CLI without editing the QA's header: flua --debug ws script.lua (comma-separated channels, e.g. --debug ws,api) — shorthand for -D debug:ws=true.

Debugging real device communications

flua's offline mode is a simulated HC3 with real network: api.* calls hit the sim's house state, while net.* (HTTP/WebSocket/MQTT clients) go to the real LAN. A QA under test therefore talks to the real device over the exact HC3 code path — without the HC3. The combination that made debugging a Sonos player straightforward:

flua --run-for 30 --debug ws SonosPlayer.lua     # sim HC3, real player,
                                                # byte-level ws trace
  • The ws trace shows every handshake and frame (see the debug section above) — with per-connection labels when several sockets are open.
  • Bounded repro runs: --run-for N caps the wall clock; a watchdog timer in the QA (setTimeout(function() _FLUA.exit(0) end, 10000)) exits cleanly once the scenario played out — the pair makes a repro QA terminate deterministically.
  • flua --version includes the Python interpreter (e.g. 3.14.3) — worth pasting into bug reports for net.* problems, since TLS behavior is version-dependent.

--%%loglength:120 caps the debug line length (default 120; a cut line ends with ...).

--%%warn:true turns on extra runtime warnings for things the HC3 never complains about, as channels:

  • status (default off, --%%warn:true enables it) — api error codes: when an api.get/post/put/delete (or api.hc3.*) returns a 4xx/5xx — or a transport failure — the emulator logs it, because most QA code silently ignores those status codes.
  • stubApi (default on) — when a QA calls one of the sim's shape-only stub endpoints (/alarms/v1/devices, /panels/climate, /users, … — see docs/rest-endpoints.md), it answers 200 in the HC3 shape but with empty/zeroed data. flua warns once per route so the limit is visible at the point of use:
[02.11.2026][FLUA   ][my-qa5000]: api GET /alarms/v1/devices is a shape-only stub in the sim (200 with empty/zeroed data) — mock it with api.registerEndpoint or run online/proxy for real controller data

--%%warn:false silences every channel; the dict form sets channels individually (--%%warn:stubApi=false). Flua's own log lines are visually distinct from QA logs: a [FLUA] level column plus the QA tag the message belongs to:

[02.10.2026][17:32:41][FLUA   ][my-qa5000]: api GET /devices/9999 -> 404

HTML in log messages

The HC3 console renders a small HTML subset in QA log lines; flua renders it to the terminal as well — print and fibaro.debug/trace/warning/ error messages only (flua's own diagnostic lines are left alone):

  • <b>/<strong>, <i>/<em>, <u> — bold, italic, underline
  • <font color="red"> / <span style="color:blue"> — text color (named colors and #rrggbb)
  • <table>/<tr>/<td>/<th> — a table with padded columns
  • <ul>/<ol>/<li> — bullet / numbered lists
  • <br/> — a line break
  • anything else loses its tags, keeping the content

With colors on, formatting becomes ANSI; with --color never (or a non-terminal) the tags are stripped instead, so the text stays readable.

QuickApp UI (--%%u)

Each --%%u: line defines one row of the QuickApp UI; several elements can share a row with {{...},{...}}. flua translates the rows into both UI property structures the HC3 understands — the legacy viewLayout and the new uiView — plus the uiCallbacks table that routes UI events to your QuickApp methods. useUiView (default false) selects the new format:

--%%u:{label="statusLbl",text="Status: Ready"}
--%%u:{button="onBtn",text="Turn On",onReleased="turnOn"}
--%%u:{switch="autoSwitch",text="Auto Mode",value="false",onReleased="handleSwitch"}
--%%u:{slider="dimSlider",text="Brightness",min="0",max="100",value="50",onChanged="handleSlider"}
--%%u:{select="modeSelect",text="Mode",value="1",onToggled="handleSelect",
--      options={{type='option',text='Economy',value='1'},{type='option',text='Comfort',value='2'}}}
--%%u:{multi="tagMulti",text="Tags",values={"1","3"},onToggled="handleMulti",
--      options={{type='option',text='Tag A',value='1'}}}
--%%u:{{button="onBtn",text="On",onReleased="turnOn"},{button="offBtn",text="Off",onReleased="turnOff"}}

Elements: label, button, slider, switch, select, multi, tabView, image, collapsible. Callbacks (onReleased, onChanged, onToggled, …) name QuickApp methods; sliders take min/max/step/value, selects and multis take options (each {type='option',text=…,value=…}) plus value/values. Values in the directive are Lua literals — strings need quotes, numbers and true/false don't. Long rows may continue on following comment lines. At runtime the device's properties.viewLayout, properties.uiView, and properties.uiCallbacks hold the generated structures, and self:updateView(elm, prop, value) updates them.

tabView, collapsible, colorPicker and colorTemperaturePicker are v2 elements. On the real HC3 the app renders them only from the uiView format — a QA using either must declare --%%useUiView:true (live-verified on 5.221 for both; the legacy $jason renderer draws neither, leaving a full-width-only view blank). flua's own viewer renders them regardless of useUiView — the requirement is about the HC3 app.

Every element takes weight=, color= and textAlign=, carried into the generated style (style.weight/style.color/style.textAlign — the HC3's own views use all three). textAlign is any CSS text-align value ('left'/'center'/'right'): it positions a label's text across the row (the HC3's labels carry it). color is any CSS color string ('red', '#ff0000', 'rgb(255,0,0)'): the HC3 applies it as a button's BACKGROUND — on a label it does nothing (the skin CSS owns the label text color; live-verified 5.221). To color label text, put HTML in the text — labels render HTML, so text='<span style="color:red">Hi</span>' works in v1 and v2. flua's viewer mirrors all of it. weight is the element's share of its container: side-by-side elements split the row width by their weights, and rows split the vertical space by their weights (flua hoists a lone element's weight onto its row) — but the HC3 app only applies the split inside FIXED-height layouts; a QA's (auto-height) UI ignores weights vertically, and weight never changes text size. An image element renders at its natural aspect, width-capped by its container (max-width:100%, height:auto on the HC3) — to make it taller use a portrait source image or give it a wider container. flua's viewer renders images the same way (natural aspect, width-capped — the weight is not a size).

Neither is editable on the HC3: the web UI editor doesn't know the elements, so it cannot edit them and an edit there can rewrite the view and drop them. Keep tabbed/collapsible QAs flua-authored and update them with --tool updateQA/uploadQA.

Child devices are the exception that makes v2 elements safe on the HC3: plugin.createChildDevice accepts a uiView and child UIs are never rewritten by the editor. A child created with a uiView initial property automatically gets useUiView = true (an explicit initialProperties value wins), so the controller renders the child from its uiView. flua --tool ui --as-lua script.lua prints the compiled UI as paste-ready Lua locals (uiView, viewLayout, uiCallbacks) to drop into the createChildDevice call — declared elements only, exactly what the .fqa package ships: the stock (embedded, __-prefixed) elements the HC3 app adds per device type are never included (--as-lua --device strips them too).

The uiView format is ONE and the same for the main QA and children — the HC3's UI editor can copy a QA's uiView as JSON and that JSON feeds createChildDevice directly, and flua --tool ui --as-lua prints exactly that format. Where a pressed button's method lives depends on which QA owns the view:

  • on the main QA, the UIAction bindings resolve through its own uiCallbacks (compiled from its --%%u declarations);
  • on a child, the binding's actionName is the method, delivered via onAction to the child's class (the classRepresentation passed to createChildDevice) with plain args — each child resolves its own methods. --as-lua --child emits these child bindings; argless bindings (buttons) must use json.array() — a plain {} JSON-encodes as an object and the HC3 app silently drops the action (live-verified).

flua's viewer executes both (UIAction via callUIEvent, direct actionNames as device actions). See examples/child-ui.lua for the child-class pattern (and UI event dispatch on the HC3 below for the full model):

Child uiViews as resources (--%%rsrc)

A --%%rsrc:name:{rows} directive declares a named child uiView — the rows are ordinary --%%u row shapes (the kind is implicit; the explicit --%%rsrc:name:u:{rows} spelling is accepted for when future kinds arrive) (one row per directive value; a bare element dict is the single-row convenience form; long values continue on following comment lines like --%%u). Repeated directives with the same name accumulate rows under the resource, like --%%u collects rows. flua compiles each resource to a child-bound uiView (actionName = the method, json.array() for argless bindings) and makes it available as fibaro.RSRC.name:

--%%rsrc:uiA:{tabView="mainTabs",activeTab="control",onTabChanged="tabChanged",tabs={
--  {name="control",text="Control",components={
--    {{button="onBtn",text="Turn On",onReleased="turnOn"}}
--  }}}}
--%%rsrc:uiC:{{{button="b1",text="1",onReleased="press"},{button="b2",text="2",onReleased="press"}},
--  {{image="art",url="https://host/art.png"}}}

function QuickApp:onInit()
  self:createChildDevice({ name = "A", type = "com.fibaro.floodSensor",
    initialProperties = { uiView = fibaro.RSRC.uiA } }, Child)
end

No rsrc.lua file is ever created for a run — the table is injected. When you package the QA, the export synthesizes one rsrc.lua (defining fibaro.RSRC with the compiled uiViews) and ships it as a normal --%%file extra, loaded before main — so the same code runs unchanged on the HC3. Resource names must be Lua identifiers (they become fibaro.RSRC.<name>); the directive is the future home of other resource kinds (icon bitmaps etc.). examples/ui-3-children.lua declares its three child UIs this way.

Resources may be declared in --%%file extras too — flua scans every QA file for --%%rsrc (the resource belongs next to the file that defines the children), collecting extras first and the main file last, so a main-file name overrides an extra's. On the HC3 the directives are inert Lua comments; the synthesized rsrc.lua carries the table. unpack/ downloadQA materialize it: the unpacked project gets a real <name>_rsrc.lua declared as an extra, with the original directives below the EOH line.

Building these UIs by hand is fine, but there is a visual path: flua --tool uibuilder [PORT] opens a web builder — a target switch (Main QA v1 / Main QA v2 / Child device), an element palette, a live preview rendered by the real viewer, and copy-out export to the --%%u/--%%rsrc directives (ADR 0016). Stateless: paste the result into your source.

An image shows a picture from its url (live-updatable via updateView(elm, "url", …); the HC3's own legacy views carry them, e.g. russound's album art). It sits inline in a row like a button:

--%%u:{image="albumArt",url="http://host/art.png"}

On the real HC3, {{device.properties.x}} templated urls and useProxy are resolved by the app client; flua's viewer renders the raw url. The viewer loads whatever a browser <img> can — including data: URIs, so inline SVGs work there (utf8 or base64). The HC3 app's image element renders no data URIs (utf8 and base64 both placeholders — live-verified 5.221); the label route (self:updateView(lbl, "text", '<img src="data:image/svg+xml;base64,…" />')) works on the HC3 only in the legacy v1 view (useUiView false), not in uiView/v2 — so a tabbed (v2) QA cannot use inline SVG art on the app and serves its art over http(s) instead. A collapsible is a full-width section header that expands/collapses its rows (the sonosGroup shape) — it must sit alone on its row, takes text, collapsed/disabled, and its own list of rows:

--%%u:{collapsible="favs",text="Favorites",collapsed=false,components={
--  {{button="play",text="Play",onReleased="play"}}
--}}

self:updateView("favs", "collapsed", true) collapses it at runtime; the viewer toggles it on click (no event — it is client-side state, like on the HC3). A v2 element — on the real HC3 it needs --%%useUiView:true like tabView (see the note above). See examples/ui-extras.lua for a runnable demo of both.

A colorPicker is the HC3's RGB color wheel (colorSpace, optional channels templates for red/green/blue) and colorTemperaturePicker its warm-temperature wheel (minTemperature/maxTemperature/ colorTemperature) — both fire onChanged with the value. flua's viewer renders them as a color input and a warm-gradient slider (approximations of the app's wheels); both are v2 elements.

A list is the HC3's data-bound list (the sonosGroup speaker rows): the element's components is the item template in the raw uiView dialect, with {{data.<field>}} placeholders wherever an item's value goes (text, button image, slider value, per-item visible, and event args) and direct actionName bindings that fire per item with the item's fields resolved (args={"{{data.playerId}}", "$event.value"}). The QA feeds plain rows at runtime: self:updateView(name, "data", { {playerId=…, playerName=…, …}, … }) — no view structure in the data. V2-only (the --check guard covers it); see examples/list.lua. Live-verified 5.22x: the HC3 app renders lists only from a plugin's packaged view file (sonosGroup's json/v2/view.json), NOT from a QA's (or child's) uiView — every template shape probed (full Sonos-style, label-only) comes back blank. Currently not usable on the HC3 from QA views; flua's viewer renders them fully, so lists are a sim/dev surface. The implementation stays for the day the app's QA pipeline catches up (or for a plugin-view bridge).

A tabView groups rows under named tabs. It is full-width — it must sit alone on its row. Tabs take name and text plus their own list of rows (the same row shapes as top-level directives); the tabView itself takes activeTab and an optional onTabChanged method, called with the event (event.values[1] is the new tab name):

--%%u:{tabView="mainTabs",activeTab="picker",onTabChanged="tabChanged",tabs={
--  {name="picker",text="Picker",components={
--    {{button="onBtn",text="On",onReleased="turnOn"}},
--    {{slider="dim",text="Brightness",min="0",max="100",value="50",onChanged="dim"}}
--  }},
--  {name="settings",text="Settings",components={
--    {{switch="auto",text="Auto",value="false",onReleased="handleSwitch"}}
--  }}}}

self:updateView("mainTabs", "activeTab", "settings") switches tabs at runtime; the viewer also switches tabs on click (sending onTabChanged when declared). See examples/tabs.lua for a runnable demo. The tabView travels in BOTH output structures — a single item in the legacy $jason body (the shape the HC3's own tabbed views use, e.g. the sonosGroup plugin) and a full-width component in uiView. A v2 element — on the real HC3 it needs --%%useUiView:true (see the note above).

Declared event handlers (onReleased, onChanged, onToggled, …) live in uiCallbacks — the table both flua and the HC3 dispatch through. For the legacy layout (the default) the .fqa follows the HC3's own export shape exactly: viewLayout + uiCallbacks only, no uiView, no event fields on the elements, typeTemplateInitialized: true, empties omitted. The uiView format travels only when it is the active one (--%%useUiView:true).

Upload: uploadFQA/uploadQA create the QA through the HC3's web-import endpoint (POST /quickApp/import, multipart) — the path the HC3's own UI uses, which preserves the package verbatim. The JSON POST /quickApp API-create path re-derives uiCallbacks with generated default names (ui<b2>OnReleased) and silently drops your handlers (live-verified 5.22x), so the tools never use it against a real controller.

At runtime a single select is set with updateView(elm, "selectedItem", value) and a multi select with updateView(elm, "selectedItems", {value1, value2, …}). Like on the HC3, an empty list must be json.array() — the marked empty array encodes as [], while a plain empty table {} encodes as an object and breaks the UI. The HC3's own demos use json.array() for exactly this:

self:updateView("tagMulti", "selectedItems", json.array())  -- [] not {}

The UI viewer

flua --ui [PORT] serves the viewer itself over HTTP, alongside the simulated HC3 API — no file to open:

.venv/bin/flua --ui 8090 examples/ui.lua   # UI viewer on http://127.0.0.1:8090/
.venv/bin/flua --ui 8090                   # no QA at all: viewer + docs, until Ctrl-C
.venv/bin/flua --docs 8090                 # straight to the docs (same server), until Ctrl-C
open http://127.0.0.1:8090/               # press Connect; the base URL matches

flua --docs [PORT] is the same server with the browser opening directly at the docs index (http://127.0.0.1:PORT/docs/) — no viewer hop. The browser opens only from a real terminal (stdout is a tty); the URL is always printed.

With no script the session just serves — the viewer, the run timeline, and the built-in docs at /docs/ (the manual ships in the wheel, so a pip-installed flua carries its own: USAGE, architecture notes, and the tutorial series).

The page defaults its API address to its own origin, so a busy port falling back to the next free one needs no editing. The page ships inside the flua package (src/flua/setup_templates/viewer/index.html is the source); --tool setup does not copy it — the served page can also point at another machine running flua.

The run timeline lives at http://127.0.0.1:PORT/timeline (linked from the viewer header): one row per QA, virtual time on the x-axis, one mark per event from the structured feed — blue api calls, green ui events, orange net operations, purple timer starts/expiries, gray lifecycle. Hover a mark for its time, QA, detail, and full data. Enable the marks with --%%trace:api,ui,net,timer (or --trace all); the page polls /flua/systemLog live, so a run under --speed/--instant draws its whole story as it happens. The buffer keeps the recent 2000 events — add --%%syslog:run.json for the complete history of a run.

Per-window URL parameters (bookmarkable): ?qa=<id> shows only that QA, ?exclude=id[,id...] hides those, ?bg=<color> / ?panel=<color> set the page/panel colors (any CSS color), and ?view=condensed starts in the condensed device list (below). The View toggle's choice is remembered in the browser, so your normal flow keeps the last mode. A panel's "open in window" button opens a ?qa= window carrying the current theme. Defaults for the colors come from the config file's viewer = { bg = ..., panel = ... } table (.flua.lua), served at GET /flua/theme.

The View toggle switches between the full panel view and the condensed device list (the HC3's compact style): every device as a small status card in wrapping rows — the value on top (sensor value + unit), the device name in bold, the log property below. Handy for runs where a QA fans out many child devices (e.g. the SolarEdge Live QA's registers); click a card to open that device's full panel.

The viewer polls GET /flua/devices (the emulated devices only — in online mode the HC3's own QAs stay out of the list), renders properties.uiView (labels, buttons, sliders, switches, single and multi selects, tabViews — styled after the HC3 look), and sends interactions back through GET /plugins/callUIEvent — the same contract the real HC3 UI uses, so your onReleased/onChanged/ onToggled/onTabChanged methods fire exactly as on the controller. Declarative deviceAction bindings (child UIs, --as-lua --child) are executed as real device actions instead — UIAction bindings stay on the callUIEvent path. self:updateView changes land live (the viewer merges device.view over the static properties). The API server stays up after the QA's timers drain, so the viewer keeps working while you tweak the file.

Two more flua-only channels round out the machine surface:

  • GET /flua/systemLog — the structured lifecycle/crash feed (the machine-readable system log the real HC3 lacks): run_start/run_stop, qa_load/qa_restart/qa_exit, boot failures, callback crashes, and engine errors as JSON entries, with last/offset polling and DELETE /flua/systemLog.
  • GET /debugMessages — the QA console buffer (QA lines with their tag, flua notices under the flua tag, runtime lines untagged), with the HC3's filter/types/from/to/last/offset query params, GET /debugMessages/tags, and DELETE /debugMessages.

On top of the QA's own UI, the viewer renders the device type's default view (the elements the HC3 adds itself): a binarySwitch gets a colored TRUE/FALSE state label and Turn On/Turn Off buttons, a multilevelSwitch adds a dimmer slider, sensors get a live value label, and so on — even when the QA defines no --%%u directives at all. A com.fibaro.hvacSystemAuto gets a thermostat panel: setpoint steppers and a slider (both resolved per mode — Auto moves each deadband side by the device's hysteresis property, Heat/Cool drive the active side in setpointStep increments, Off disables them), the displayed target (the heat/cool average in Auto), and Auto/Off/Heat/Cool buttons calling setThermostatMode. com.fibaro.hvacSystemCool/com.fibaro.hvacSystemHeat share the same panel with only their side: Off/Cool or Off/Heat mode buttons, steppers and slider driving setCoolingThermostatSetpoint/setHeatingThermostatSetpoint. The viewer fetches them from GET /flua/embeddedUI (a flua-only channel) and prepends them above the custom UI; the elements are never stored in the device's viewLayout/ uiView properties, so they cannot leak into a .fqa export. Their controls invoke device actions (POST /devices/{id}/action/{name}), and their labels track the watched device properties (e.g. value), both exactly as the HC3 client behaves. The definitions live in a table in src/flua/devices/uielements.py — add a QA type there to give it a default view.

For the real HC3 UI, use proxy mode instead (--%%mode:proxy): the mirror QA on the HC3 renders the genuine UI and funnels every interaction back to the emulated QA.

The virtual clock starts now unless you set a start time — handy for testing dates: leap years, DST switches, New Year logic. Combine with --instant to fast-forward through the interesting moments:

The Lua config file

.flua.lua (in the directory you run from, or ~/.flua.lua; the legacy ~/.plua/config.lua also works) is Lua data, loaded once and merged into _FLUA.config — handy for per-machine settings:

-- .flua.lua
return {
  user = "alice",
  pwd = os.getenv("HC3_PASSWORD"),   -- reads the .env chain
  colors = { "red", "green" },
}

QA code sees it as _FLUA.config.user, and --%%var expressions can use it: --%%var:color=config.colors[1]. --%% annotations win over the file. A faulty --%%var expression (a syntax error, indexing a nil key) is a startup error — flua names the variable and exits 1 — but an expression that evaluates to nil (config.foo, os.getenv("MISSING")) simply leaves the variable unset.

Variables in packages

A --%%var can declare a package value: a quoted string after the last top-level comma of the expression — --%%var:pwd=config.secretPwd,"<set to service password>". Commas inside the expression (table literals) or inside the placeholder itself are fine. --%%clobber:name=value is the legacy Plua spelling of the same thing.

Which value lands in a package depends on where the package goes:

  • Distribution (--tool pack, flua export, the .fqa you share or post on the forum): the package value, the evaluated value when no package value was declared. The main file's --%%var header lines are rewritten to these literals, so no expression — and no secret literal — travels in the file content.
  • Your own HC3 (--tool uploadQA as a new QA): always the real evaluated values — the placeholder is a distribution concern, your controller gets the credentials the QA needs.
  • --tool updateQA never syncs variables: they are initializers, and the runtime values on your HC3 win.

Packaging evaluates the expressions the same way bootstrap does ({config, os} in scope) but never loads or runs QA code — a faulty expression is a loud packaging error naming the variable, and an expression that evaluates to nil leaves the variable out of the package.

A location table configures the simulated controller's location — device 1's sunriseHour/sunsetHour are computed from it:

return {
  location = { latitude = 59.3293, longitude = 18.0686 },  -- Stockholm
}

Precedence: the built-in default (Stockholm) < the db/seed file's location < .flua.lua < --%%location (the main QA's directive) < a runtime PUT /settings/location. Combine it with --%%time:start=... for a fully deterministic sun: a known place on a known date.

The configured location is the sim's full /settings/location shape (timezone, city, units — PUT merges any scalar) and drives more than sun times: /panels/location's home panel (219) reports its lat/long, and /settings/info's date, timestamp and sun fields follow the virtual clock — the virtual-clock fields stay sim-side even in online mode, so QAs reading devices/1 see simulated time. Offline, /weather uses the location's units for its fake record (online, the real HC3's weather and units are served instead — see below).

To set up specific controller values for a simulated run, QAs PUT the same endpoints the HC3 accepts: /settings/info (any scalar field — hcName also renames device 1), /home (scalar fields + defaultSensors/ notificationClient wholesale), and /panels/location/{id} (name/radius/ address/home). The virtual-clock fields (sun times, date, timestamp, serverStatus) stay computed and ignore PUTs. GET /weather serves the real HC3's weather in online mode (the provider owns it there); offline it is the sim's stable fake HC3-shaped record. PUT /weather is a flua extension (the HC3's weather is provider-owned): it merges overrides on top of the current record — only the fields in the body change — and each field that actually changes emits one WeatherChangedEvent (change/newValue/oldValue) on the refreshStates feed, so scene logic can react to a fixed forecast; re-PUTting the same value emits nothing.

os.getenv(name) reads through flua's environment chain: the shell environment first (so explicit per-run settings like CLI flags win), then the local .env in the directory you run from, then ~/.env as the global fallback. Files are plain KEY=value lines (comments and quotes supported) and are re-read when they change — handy for API tokens and per-machine settings that don't belong in the QA code.

The --%%include defaults directive

A QA can pull its defaults from another file — per-QA, explicit, and the path resolves relative to the main file (like --%%file):

--%%include:defaults.lua      -- inserts that file's directives as defaults
--%%name:LocalName            -- this QA's own directives override them

-- defaults.lua — same --%% directive syntax as a QA header
--%%mode:offline              # this project normally runs offline
--%%description:local playground QA

The included file's directives are defaults: the QA's own win per key, the mode family overrides as a whole (a QA can opt out of an included --%%mode:offline), and --%%file lists append (defaults first, a redeclared name wins). Includes nest — each path relative to the file carrying the include line — and a --%%file declared inside an include resolves relative to that include's own directory (a file directive always means relative to the file that declared it). Cycles are skipped; a missing include is a loud error. Note that Lua's own file I/O (io.open/dofile) stays cwd-relative — QAs that read project files by relative path must be run from the project root (flua never chdirs). This replaces the old .directives working-directory defaults (the file was ambiguous when QAs lived in different subdirectories — each QA now declares its own defaults explicitly).

Migrating from plua

plua projects migrate with a mostly mechanical pass: flua --tool migrate . scans the project for every plua-ism in one pass (directive spellings, script invocations, stale packages, baked IPs — exit 1 until clean), and flua --check covers the syntax. Two legacy spellings are accepted so old QAs run unchanged — --%%name=value (the pre-plua = form, parsed like :) and plua's --%%headers:FILE (an alias for --%%include); respell both when convenient. The remaining renames:

  • --%%headers:FILE → --%%include:FILE (accepted as an alias — respell; paths relative to the declaring file)
  • -- %%save/-- %%port → gone (flua export -o / --tool pack -o)
  • -- %%proxy:true → --%%mode:proxy; --%%conceal → --%%clobber
  • tools: plua -t pack SRC OUT → flua --tool pack SRC -o OUT -f; the uploadQA/updateQA/downloadQA/uploadFile names carry over
  • behavior: --api remote overrides the main QA's --%%mode:offline; plugin.restart() aborts the current turn like the HC3; --instant and --step are both deadline-ordered fast-forward (each callback observes its own deadline in os.time()); tag perpetual housekeeping loops _FLUA.background(fn)

The full checklist, the verified emulated-surface matrix, and the gotchas from real migrations live in the plua-migration skill (flua --tool setup installs the skill pack).

The .flua-directives override file

Testing someone else's QA usually needs one or two overridden values — a password, an IP — without editing the QA (or VS Code's launch.json). .flua-directives, next to the QA's main file, is that file: the same --%% syntax as a QA header, applied as if its lines came after the QA's own — the tester wins:

-- .flua-directives — next to main.lua; the QA's own --%%var:pwd/--%%var:host lose
--%%var:pwd=os.getenv("HC3_PASSWORD")   -- expressions work: the .env chain included
--%%var:host="192.168.1.99"
--%%mode:offline                        # or any directive, including globals

Discovery keys on the directory of the path given on the CLI: the main file's directory, and for a .fqa the package's own directory (a .flua-directives inside a package is the author's file and never auto-applies). Every QA listed on the command line checks its own directory, so QAs in different directories each get their own overrides; a missing file is simply skipped. The file wins over the QA's header and its --%%include defaults; explicit -D flags win over the file. Global directives (--%%time, --%%db, ...) work too — they land in the run's shared config, like -D does. The file often holds secrets: gitignore it, or keep it expression-only (os.getenv(...)), reading values from the .env chain.

Multi-file QAs

On the HC3 a QA is a set of named Lua files — one is main. flua keeps your files on disk and declares the extras in the main file:

--%%file:lib.lua,lib
--%%file:util.lua,util
-- --------------- EOH ---------------
print(helper())

Files load in declaration order, main loads last. Paths resolve relative to the main file's directory. A $ prefix instead loads a library bundled with flua (src/flua/lua/lib/, shipped in the wheel — plain Lua, so it also runs on the HC3 and travels in the .fqa like any QA file):

--%%file:$event_mgr.lua,em   -- flua's bundled event-manager library

A missing bundled library (or a path-escape attempt like $../x.lua) is a loud load error. See examples/multifile.lua. The HC3's file API works offline too (api.get('/quickApp/' .. _FLUA.qaId .. '/files') etc.).

--%%file files are the QA's shipped files — they travel into the .fqa (--tool pack, uploads). The declared file NAME is the name on the controller: the HC3's upload accepts anything, but its file editor refuses to open odd names (identifier-like is required — a hard error) and names under 3 characters (only a warning: the HC3 accepts them, the editor just will not open them). The default name (derived from the path when no name is declared) keeps today's behavior. Test-only helpers (mock-server handlers, assertion libraries) can stay out of the package: plain Lua require("name") finds name.lua next to the main file at runtime, and require'd files are never packaged.

Classes (class)

class(name) is the HC3's Lua class helper — flua implements the HC3's (undocumented) contract, which matters when you port QAs that build their own class hierarchies (the Fibaro manual documents net.HTTPClient and friends but never class itself). The contract:

  • class("X") installs the class object as the global X and returns the parent-setter, not the class. To get the class object itself, read it back — real-HC3 QAs do the same dance, so this is HC3 behavior, not a flua quirk:

lua class 'MyDevice'(QuickApp) -- the returned function sets the parent local MyDevice = _G.MyDevice -- the class object

  • Instantiation asserts the class defines its own __init — a parent's __init is not inherited. Every subclass declares its own and chains the parent explicitly:

lua class 'A' function A:__init(v) self.v = v end class 'B'(A) function B:__init(v) A.__init(self, v) end -- no implicit inheritance local b = B(42)

Methods are inherited (the class metatable's __index chain) — only the constructor must be redeclared per class.

The offline HC3

Online mode — the real HC3

The backend is picked from the main QA's directives — -D flags and .flua-directives over its header over any --%%include'd defaults (see below), before the engine starts:

  1. an explicit --api local|remote always wins;
  2. otherwise, --%%mode:online/--%%mode:proxy in the main QA's directives selects the real HC3, --%%mode:offline the offline sim;
  3. otherwise, offline — the default: the simulated HC3, no credentials needed. Online is opt-in (--%%mode:online|proxy, or --api remote), and requires HC3 credentials in the environment (HC3_URL/HC3_HOST); without them flua exits with an error.

--%%mode:offline on a secondary QA pins just that QA's api.* calls to the sim while the rest of the run stays online — handy for keeping test QAs sandboxed against a live controller. An explicit --api remote also overrides the MAIN QA's own --%%mode:offline pin (the flag outranks the header — the main QA's pin drove the engine mode, and the flag wins); secondary QAs' pins always hold. The legacy --%%offline:true is an alias for --%%mode:offline.

With --api remote, the api table talks to the real HC3: the controller is authoritative for its resources — reads of rooms, scenes, sections, globals, custom events, profiles, alarm partitions, panels, users and the like come from the HC3. The sim's base structs (device 1, /home, /settings/info, /settings/location) are the controller's real structs fetched lazily on first access, with the virtual-clock fields (sun times, date/time) computed on top. What the emulator created locally (emulated QAs from id 5000, scene QAs) merges into those views (/devices, /plugins, /scenes), and writes stay in the emulator (they do not mutate the controller). Anything the sim doesn't know is forwarded to the controller over HTTP — the same Lua surface, hybrid routing. Remote calls are asynchronous per QA: a slow controller call suspends only the calling QA (its timers and events queue, like during fibaro.sleep) while the pump and every other emulated QA keep running — the response resumes the QA's code exactly where api.get was called. Offline (the default), calls stay synchronous — the fast path. Credentials come from the .env chain:

# .env
HC3_URL=http://192.168.1.10/
HC3_USER=admin
HC3_PASSWORD=your-password
HC3_PIN=1111

.venv/bin/flua --api remote script.lua

Remote calls are synchronous (like on the HC3) — each api.get blocks the QA for the HTTP round trip. Credentials are never retried: a 401/403 stops flua immediately with a warning, because the HC3 locks itself after 4 failed attempts. Wrong credentials = one attempt, then exit 1.

api.hc3.get/post/put/delete always targets the real HC3 directly, bypassing the hybrid dispatch (this is what fibaro.callhc3 uses, and it's handy in test code that wants ground-truth data). Offline it stands in for the simulated HC3.

The FluaHelper bridge (the HC3's local-only API)

The HC3 serves part of its API only to LOCAL callers: the single-key QA variable endpoints (GET /plugins/{id}/variables/{key}) and the variable writes (PUT/POST/DELETE) refuse external callers, while the list endpoint works fine. For those, flua deploys a small invisible helper QA on the controller that executes calls in the local context and reports back over a WebSocket:

flua --tool installHelper        # uploads FluaHelper; it waits idle for flua's wake
flua --api remote my-qa.lua      # the helper server (a free OS-assigned port by default)

The port is advertised to the helper on every wake (its connect action carries the ws:// URL it dials back to), so it only has to match between the server bind and the wake — it never needs to be stable across runs. By default the OS picks a free port, which also means several flua instances in parallel on one machine just work; pass --helper-port N only when you need a fixed port (e.g. a firewall rule).

The helper auto-detects this machine's LAN address (a UDP route probe; --tool installHelper --host IP overrides). It never re-dials on its own: after a disconnect it sits idle until flua needs it — then flua discovers it by quickAppUuid, fires its connect action through the HC3, and waits for the dial-in before sending the RPC. One helper serves many flua machines at once (a connection per ws:// URL); re-asking with the same URL replaces the stale connection. Re-running installHelper is safe and idempotent — it finds the helper by its quickAppUuid property (never by name, so a renamed QA stays recognized), keeps the newest, removes any older or duplicate copies, and re-points the survivor at this machine. From a QA, calls route through it:

local value, status = api.helper("GET", "/plugins/4357/variables/heat", nil)
api.helper("PUT", "/plugins/4357/variables/heat", { name = "heat", value = "2" })

api.helper suspends the calling QA like any remote api.* call and returns (data, status) — (nil, 0) when the helper is not installed or not connected (the run log says so, pointing at installHelper). The helper server binds 0.0.0.0 (the controller must reach the laptop); your OS firewall may ask about Python once.

In online/proxy mode the routing is transparent too: api.* calls to the variables endpoints on an HC3-namespace id (below 5000 — the controller's own QAs) automatically go through the helper, exactly like the other REST endpoints forward to the HC3. Emulated ids (5000 and up) stay in the sim; offline, only emulated ids are served.

In proxy mode a proxy QA's own variables — and its children's — route through the helper: reads answer from the real HC3 device, and writes run there first with the sim shadow mirroring on success (the property-update pattern, minus the event dedup — variable writes carry no refreshState event). The state lives on the controller and survives flua reruns without an explicit db (children included, so libraries like QwikChild that store their state in child variables keep it).

-- online mode, reading another QA's storage on the controller:
local v = api.get("/plugins/4366/variables/x")   -- via FluaHelper, returns the var

The same bridge runs controller-side fibaro.* functions — the real HC3's Lua surface, for parity probes or real device actions:

local globals = api.helperFibaro("getGlobalVariable", { "HomeStatus" })
api.helperFibaro("call", { 88, "turnOn" })     -- acts on the REAL device 88

api.helperFibaro(name, args) executes fibaro[name](table.unpack(args)) inside the helper QA and returns its values (nothing on failure — a warning is logged). It runs in the helper's context: the QA's own id and source-trigger data are the helper's, and actions affect the real controller. Avoid fibaro.sleep — it would block the helper's thread and drop the connection.

Proxy mode (--%%mode:proxy)

To test a QA against its real UI in the phone app — or against scenes and other QAs on the controller — flua can deploy a proxy QuickApp on the HC3 (the proxy concept). The QA keeps running in the emulator while a proxy device named <name>_Proxy (same device type, same UI) runs on the HC3, and the two are treated as one device:

--%%mode:proxy
  • The emulated QA runs with the proxy's HC3 id — actions and UI events aimed at the proxy land in the emulator.
  • The proxy funnels everything back: device actions are forwarded to http://<your-ip>:<port>/api/devices/<id>/action/<name> and UI events to http://<your-ip>:<port>/api/plugins/callUIEvent; the emulator runs them through the QA's callAction/UI callbacks exactly like a tap in the real UI.
  • When the QA updates a property or a UI element (self:updateProperty, self:updateView, self:setVariable), flua pushes the same update to the HC3, so the proxy always reflects the emulated state.
  • Property changes produce one refreshStates event: the HC3 proxy emits it and the poller mirrors it back — flua does not generate a second, local event.
  • Children: self:createChildDevice creates them on the HC3, and children an existing proxy already has are shadowed in the emulator under their HC3 ids at startup — the QA's initChildDevices() finds them, their property updates are stored locally and forwarded, and their actions/UI events route back through the proxy like the parent's.
  • Internal storage (self:internalStorageSet/Get, api.* on /plugins/<id>/variables): reads go to the HC3 device via the FluaHelper bridge (authoritative), and writes update both — the controller first, then the sim shadow mirrors on success, exactly like property updates. Variable writes carry no refreshState event, so there is no event dedup to do. The proxy (and each child) keeps the state on the controller, so it survives flua reruns without a db.
  • Don't run the same QA in proxy mode from two flua instances in parallel — both deploy a proxy with the same name on the HC3 and fight over which flua the proxy sends actions and UI events back to. Testing the same QA in parallel works in plain offline/online mode; proxy mode is one instance per QA. api.delete( '/plugins/removeChildDevice/' .. id) deletes a child on the HC3 and drops its emulated shadow (offline it just removes the local child).

An existing <name>_Proxy is reused (duplicates are deleted, the newest wins; a proxy of the wrong device type is deleted and recreated). On reuse flua refreshes the proxy's viewLayout/uiView/uiCallbacks from the QA's current --%%u directives, so UI edits between runs show up on the controller. With --%%mode:proxy,noUI flua never pushes the UI instead: a reused proxy keeps whatever the HC3 editor holds, and a fresh proxy deploys with empty UI shapes for you to build in the editor — fetch the result back with flua --tool ui --device <id> (renders --%%u rows plus the raw UI JSON) and adopt what you want into the QA. useUiView is only pushed when the QA declares --%%useUiView — otherwise the proxy keeps whatever you configured on the HC3 (the legacy viewLayout still has features the new uiView lacks), and a fresh proxy defaults to true. On startup flua tells the proxy where to listen back through a CONNECT action, so an existing proxy always points at the current emulator.

Proxy mode only works online: without HC3 credentials flua logs proxy disabled and runs the QA offline as usual. A proxy QA also keeps flua alive past idle (like --%%keep-alive:true) — it must stay up to serve the proxy's callbacks.

The emulator listens for callbacks on all interfaces, port 8080 by default (FLUA_PROXY_PORT in the .env chain overrides it; busy ports fall back to the next free one). Your machine and the HC3 must be on the same network, and your firewall must let the controller reach that port.

Testing against the real HC3

Two opt-in suites, gated so a plain pytest never touches the controller (set HC3_TEST=1 and configure the credentials in the environment):

HC3_TEST=1 .venv/bin/pytest tests/test_hc3_live.py    # lifecycle: read-only + upload/call/delete
HC3_TEST=1 .venv/bin/pytest tests/test_hc3_compat.py  # shape oracle: sim vs real HC3

The lifecycle suite is production-aware: read-only checks (settings, devices, globalVariables, refreshStates), one import of a test QA (its startup, fibaro.call round-trip, and its refreshStates change feed are verified), then deletion — only the test QA is ever touched. Wrong credentials cost exactly one attempt (the lockout guard).

The compat suite runs the same requests through the offline sim and the real HC3 and diffs the response shapes: type mismatches and fields the sim serves that the HC3 doesn't are failures; fields the sim doesn't model yet are reported as gaps.

RefreshStateSubscriber (the refreshStates subscriber class) works in both modes: offline, sim state changes (device creation/removal, property updates, actions) are emitted as real-shaped DeviceCreatedEvent / DeviceRemovedEvent / DevicePropertyUpdatedEvent / DeviceActionRanEvent events — updateProperty only emits when the value actually changes — and online, the poller long-polls the real HC3's refreshStates and mirrors its events into the same feed. Both arrive at subscribers through the message pump as a refreshStateEvent message.

The poller never keeps flua alive by itself: online runs still exit when no timers, messages, or connections are pending. A QA that must keep running past idle — waiting for HC3 events like it would on the controller — opts in with a directive:

--%%keep-alive:true

While a loaded keep-alive QA is running, flua holds the HC3's long poll and stays up until the QA exits (or Ctrl-C; a fixed --run-for -5 also works); without the directive the poller still mirrors events for the running QAs, but never holds the process open — a drained run exits promptly. Ctrl-C always terminates flua immediately, even mid-long-poll, and exits with status 130.

--seed loads a simulated house (see examples/house.json):

.venv/bin/flua --seed examples/house.json script.lua

Your QAs become devices (ids from 5000) in the same simulated HC3, so everything works between them:

  • api.get/post/put/delete — the real HC3 REST surface (devices, plugins, variables, globals, scenes, alarms, profiles, refreshStates, …)
  • fibaro.call(id, 'turnOn') — calls another QA's QuickApp method
  • fibaro.emitCustomEvent(name) → QuickApp:onCustomEvent(name) handlers
  • self:setVariable/getVariable — persistent, survives restarts; --%%var values are visible through api.get('/devices/<id>').properties.quickAppVariables already during onInit (the HC3's initialProperties behavior)
  • plugin.restart(id) — re-runs the QA's code (onInit runs again, like the HC3 restarting the plugin); timers are cancelled and deferred messages dropped — and like the HC3, the call kills the current turn: code after plugin.restart() never runs
  • GET /refreshStates?last=N — the HC3's polling change feed

QAs find each other by name with fibaro.getIds({type = "quickApp"}) — see examples/qa3.lua and examples/qa4.lua calling each other.

Loading QAs at runtime

From VS Code you often run one QA — let it bring up the QAs it needs:

local id = _FLUA.loadQAfromFile("examples/qa3.lua")   -- annotations parsed
local id2 = _FLUA.loadQAfromString([[ ...inline QA... ]])
local id3 = _FLUA.loadQAfromFile(                      -- extra directives
  "examples/qa3.lua",
  { "var:friend=42", "property:value=true" }
)
fibaro.call(id, "turnOn")   -- immediately reachable

The optional second argument is a table of directive strings, applied as if appended to the loaded QA's --%% header: var/property merge per key (the QA's own variables survive), u/file append, everything else overrides. Both functions return the new QA id (or nil, error). examples/dynamic.lua demos it.

Simulated devices ship inside flua — src/flua/simdevices, bundled in the wheel, so pip-only installs have them too — and load by bare name:

local temp = _FLUA.loadSimDevice("temperatureSensor")  -- throws on unknown name
fibaro.call(temp, "setValue", 21.5, "C")
local motion = _FLUA.loadSimDevice("motionSensor")
fibaro.call(motion, "breach")
-- like loadQAfromFile, an optional second argument overrides the device's
-- --%% header: rename it, preset its properties — one bundled device
-- becomes any number of distinct devices
local hall = _FLUA.loadSimDevice("temperatureSensor",
  { "name:Hall temp", "property:value=21.5", "property:unit=C" })

The bundled set mirrors the quickapp-types device templates (temperatureSensor, humiditySensor, motionSensor, doorSensor, windowSensor, smokeSensor, floodSensor, binarySwitch, multilevelSwitch, colorController, the HVAC trio, alarmPartition, weather, player, … — the full template set). Every sim device keeps itself alive for the whole run and answers fibaro.call: value sensors take setValue(value, unit?) and setUnit(unit); breach sensors take setValue(bool), breach(), clearBreach() (the sensor's value IS the breach state — there is no separate breached property on sensors); switches take turnOn/turnOff/setValue; controllers keep their stock actions (arm/disarm/setArmed, setThermostatMode, setHeatingThermostatSetpoint, setColor, createChild, …). Drive one and watch scenes and reacting QAs fire like on a real device.

Sensors also carry a UI for the web view (the --ui/builder tab): every binary sensor (motion, door, flood, smoke, …) gets Breach/Clear buttons, and every multilevel one (temperature, humidity, light, meters, …) a slider over its real range and unit. Tapping them in the view is exactly a callUIEvent — the sensor's value changes and reacting QAs notice, so the view doubles as a test bench. The initial value is a number (0), never the skeleton's empty string, so recipes comparing value > threshold cannot crash against it.

alarmEndpoint is the system-level one: it serves the /alarms/v1/* endpoints with the HC3's partition model — the built-in partitions, deployed com.fibaro.alarmPartition QAs (arming dispatches to the QA's own arm action), and partitions created via POST /alarms/v1/partitions.

Network clients

Real network, HC3-style APIs, all asynchronous through the pump (callbacks run in your QA, timers keep running while requests are in flight):

  • net.HTTPClient({timeout=ms}) → request(url, {options, success, error}) — examples/http.lua (constructor timeout sets the per-request default; options.timeout overrides it. options.checkCertificate = false skips HTTPS certificate verification, like the HC3 — handy for self-signed certs; the default verifies) SSE: a text/event-stream response streams — success fires per raw event block ({status, data, headers}), and the stream ends silently when the server closes (the HC3's behavior); a mid-stream read timeout is a transport failure and reaches error — real services send keepalives just inside typical read timeouts (Hue ≈ every 58s), so treat mid-stream timeouts as transient: catch and reconnect, don't fail the QA. exit() cancels the QA's in-flight requests — an open stream dies with its QA. Loopback: on the HC3, 127.0.0.1/localhost is the controller — every port, the public web server included (the /assets icon tree lives there). Online, flua rewrites ALL loopback URLs to the configured controller with the configured credentials — the same hack QAs on the HC3 use to avoid embedding credentials (an explicit Authorization header or embedded userinfo wins). A QA that wants the dev laptop instead uses _FLUA.hostIP — a real LAN address, never loopback, never rewritten (guard with _FLUA and _FLUA.hostIP or "192.168.1.99" for HC3 portability). Offline, only the controller's 11111/11112 surface stands in at a running --ui API server; every other loopback URL stays local (mock servers on the laptop), so controller QA code that calls its own loopback API — e.g. installing an .fqa over multipart — runs unchanged in the emulator.
  • net.TCPSocket({timeout=ms}) → connect/send/write/read/readUntil/close — examples/tcp.lua (write is the HC3-documented alias of send)
  • net.UDPSocket({broadcast, timeout}) → sendTo/receive — examples/udp.lua
  • net.WebSocketClient()/WebSocketClientTls() → addEventListener, connect, send, sendBinary — examples/websocket.lua (connect(url, headers) takes a headers table, like the HC3; sendBinary sends binary frames, and dataReceived(payload, isBinary) receives them — the new HC3 binary mode). The 5.221 semantics are matched: Sec-WebSocket-Protocol entries split on commas, join canonically, and reject non-HTTP tokens with an error; send() rejects non-UTF-8 text with an error pointing at sendBinary; close() before the handshake completes delivers only disconnected. Like the HC3, the TLS client does not verify certificates by default (embedded bridges ship self-signed certs — e.g. Dirigera); the flua extension connect(url, headers, {checkCertificate = true}) opts back into verification. examples/mqtt-over-websocket.lua shows the 5.221 pattern of building MQTT in Lua on top of the client (varint/mqttString packet assembly, the receive accumulator) — binary payloads arrive latin-1-decoded (one char per byte, 0–255), so string.byte round-trips exactly.

Socket lifecycle (reconnect semantics): ws:close() fires the disconnected listener exactly once (whether the handshake had completed or not — closing before it delivers only disconnected, pinned). A client instance owns one connection; for reconnect logic the supported pattern is a fresh client per reconnect (construct → connect → listen), not re-connect() on a failed/closed instance. The server side mirrors it: disconnected fires once per connection, and a server-side ws:disconnect(conn) closes the connection from the listener's side. - mqtt.Client.connect(uri, options) → subscribe/publish/unsubscribe/disconnect, mqtt.QoS — examples/mqtt.lua (mqtts:// or options.tls enables TLS: useSNI on by default like the HC3 ≥ 5.191, tls.useSNI = false switches SNI off; also allowUnauthorized, certificateAuthority, clientCertificate)

TCP/UDP payloads are binary-safe: raw bytes (including NUL and values above 0x7F) cross the bridge byte-for-byte in both directions — a payload is escaped for the message bridge and un-escaped on the wire, so even a literal \x sequence in your data round-trips intact.

Mock servers (net.*Server)

A flua extension (no HC3 counterpart): a QA can host mock servers so its net.* clients can be tested without a controller or Python. The handler runs in the QA on every request; its return value is the reply. All servers bind 127.0.0.1; port 0 picks a free port (server.port).

local http = net.HTTPServer()
http:listen(0, function(req)               -- {method,url,headers,body}
  return {status = 200, body = "ok", headers = {["X-Mock"] = "1"}}  -- or a string, or nil (204)
end)
local tcp = net.TCPServer()
tcp:listen(0, function(data, conn) return data:upper() end)
  -- one handler call per request; return the reply, or nil for no reply.
  -- The connection stays open until the CLIENT closes it; conn is a stable
  -- per-connection id for per-client state. Payloads are binary-safe
  -- (raw bytes arrive and return byte-exact).
local udp = net.UDPServer()
udp:listen(0, function(data, ip, port) return "got:" .. data end)  -- nil = no reply
local ws = net.WebSocketServer()
ws:listen(0, function(message, isBinary, conn) return "echo:" .. message end)
  -- ws handlers get the stable per-connection id too — and the server can
  -- push UNSOLICITED frames (event-driven protocols, Sonos-style):
  --   ws:send(conn, data) / ws:sendBinary(conn, data)  one connection
  --   ws:broadcast(data)                               every open connection
  --   ws:disconnect(conn)                              server-side close
  --   ws:addEventListener("connected"/"disconnected", function(conn) ... end)
...
http:close()

Semantics: HTTP is one-shot (request/response); TCP keeps the connection open across requests until the client closes, UDP is one datagram in, optional reply out, and WS is message-based with optional replies plus server-initiated pushes. WS binary messages echo back as binary frames, byte-safe, and TCP/UDP/WS payloads cross the engine bridge byte-safe. A handler that raises replies 500 (HTTP) or nothing; a handler that never returns answers 504 after 10 s. Mock scaffolding can live in a sibling file loaded with require — it runs in the QA's own environment (so it can use net.*Server, fibaro, timers directly), and stays runtime-only, never part of the .fqa package. Guard the line so the QA still runs on the real HC3, where require does not exist:

if require then require("mocklib") end  -- flua only; no-op on the HC3

See examples/mockServer.lua — a QA that hosts all four and verifies its own clients against them.

The HC3 QA sandbox

A QA on the real HC3 runs in a restricted Lua environment: the HC3's QA template (quickApp.lua, loaded for every QA) nils the following globals after its own requires — verified on a live HC3 5.221:

  • coroutine — QAs are callback-only: setTimeout/setInterval, net.* callbacks, RefreshStateSubscriber. flua's coroutine model (fibaro.sleep, per-QA coroutines, the async pump) is an emulator extension — guard it with if _FLUA then ... end when the QA must also run on the HC3.
  • require — gone too (removed by the plugin runner, not the template), so QAs cannot load Lua modules on the HC3; neither --%%file includes nor flua's bundled $ libraries exist there.
  • load, loadfile, loadstring, dofile, module, getfenv, setfenv, debug, file, io, package, rawequal, rawget, rawset
  • os.execute, os.getenv, os.remove, os.rename, os.setlocale, os.tmpname — the rest of os (time, date, clock, difftime) stays available.

Scenes run under a separate whitelist environment that is at least as restricted (no require, io, package, coroutine either). flua does not sandbox QAs — the emulator is a development tool. The compatibility contract is therefore the reverse one: a QA that stays inside the HC3's sandbox surface runs the same in flua; flua-only conveniences must be guarded, or the QA stays emulator-bound.

Loading files into a QA's environment

flua keeps the loaders the HC3 nils, but which environment a loaded file runs in is easy to get wrong. Inside a QA, the QA's _G is its own environment (fibaro/api/net live there); the shared runtime _G has none of them. Which one each loader uses:

  • require("name") — rebound per QA: the file loads and runs in the QA's own environment, so it can use fibaro, timers, net.*Server directly.
  • dofile(path) — rebound per QA the same way (flua-only: the HC3 nils it). A dofile'd file behaves like a --%%file include, but is never packaged.
  • _FLUA.loadFile(path) — the sanctioned loader for harness/test code that drives a QA's real files at runtime. Returns a chunk bound to the QA's environment (call it to run): same env as dofile, but explicit, so tooling never needs to know about the _G aliasing.
  • Raw load/loadfile — stock: with no env they compile against the shared runtime _G, where fibaro/api/net are nil. To run a loaded file with QA globals, pass the QA's own _G: loadfile(path, "bt", _G). (On the real HC3 all of these are nil; any use of them is flua-only.)

UI event dispatch on the HC3 (QA, children, v1, v2)

How an interaction becomes a method call — observed live on 5.221; the model below is our best reading of that behavior. Two channels exist:

  • deviceAction execution: the app executes each eventBinding entry as a device action; the runtime's onAction(deviceId, action) calls callAction(action.actionName, action.args…) on the main QA, or on the child instance when the id is a child's.
  • UIEvent resolution: an event {elementName, eventType, values, deviceId} feeds onUIEvent, which looks up uiCallbacks[elementName][eventType] — the main QA's table, registered at boot from properties.uiCallbacks (--%%u compiles it; children never register one).

How each format uses them:

  • v1 viewLayout (main QA): $jason elements carry no event fields — the event→method mapping lives only in properties.uiCallbacks. The app delivers UI events on the UIEvent channel; the QA method receives the event table (e.values[1]).
  • v2 uiView (main QA): bindings carry UIAction (actionName='UIAction', args={eventType, elementName, [value]}) — the back-compat action on QuickAppBase that converts the call into a UIEvent and feeds the same uiCallbacks resolution. Same delivery, newer transport.
  • v2 uiView (child): the binding's actionName is the method, executed as an action on the child → child:callAction(actionName, args…) → the method on the child's class (the classRepresentation passed to createChildDevice), with plain args. $event.value templates resolve to the interaction's value; an argless binding must use json.array() — a plain {} encodes as an object and the app silently drops the action.

One asymmetry worth knowing: the same slider hands over its value differently — the main QA's method receives an event table (dim(event), value in event.values[1], v1 and v2 alike), while a child's method receives the value directly (dim(value)). Same uiView format, different signature.

flua mirrors all of it: the viewer executes non-UIAction bindings as device actions and UIAction bindings via callUIEvent, and the sim's onAction/onUIEvent route the same way (child:callAction, the main's uiCallbacks lookup) — so a QA behaves identically in the sim and on the controller. The child recipe is examples/ui-3-children.lua.

Recipes are recipes/<id>/{main.lua,manifest.json} in the flua repo, fetched live by the builder (one merge, no release). The manifest declares the title/description/categories/params — a device param's filter is an isTypeOf base type for its picker — and optionally simDevices: bundled sim devices loaded into the sim run alongside the picked devices, so the user can drive the recipe's world from the web view (the weather manager and its sliders for heat-when-cold). An optional verify block declares the scenario --verify runs: the params to seed, the steps (device calls, weather changes, UI slider drags, virtual waits), and the expected outcomes; a start anchors the virtual clock — {time="12:00"} (today at noon, safely before sunset), a full date-time string, or {before="sunset", by="2m"} for short sunset timers — and a waitUntil step advances virtual time until a device reaches a value (with a timeout). scripts/gen-recipes-index.py regenerates the index and validates every field.

Offline — or before the real sensor is installed — the builder's device pickers also offer the bundled simulated devices that fit the param's type filter: picking one keeps the variable at 0 (the recipe prints its hint until a real id is set) and the sim run seeds exactly that device, so the whole generate → simulate → view loop works without an HC3.

The HC3's standard icon library (~13,000 state files, ~65 MB) is Fibaro copyrighted artwork, so flua ships only the manifest (devices/ icon_manifest.json, built by scripts/extract_icon_files.py — live-probed from the HC3: every set serves 14 state suffixes in both png and svg). --tool icons download fetches the images once into a machine-level cache (~/.flua/icons, FLUA_ICON_DIR overrides) — one cache per user, shared by every project, never per repo. Against a live HC3 the tool also enumerates the controller's icon library and downloads the sets the manifest does not cover: newer-firmware additions (their files follow the same 14-suffix pattern) and custom icons uploaded with uploadExternalIconSet. A custom User<id> set lives in /assets/userIcons/devices/ as <set><state>.png — the base for single-icon sets, ladder states (0..100) for binary/multilevel sets, named states for shutter sets — while its /assets/icon/fibaro/ slots hold placeholder art (the declared .png slot serves an SVG body). The downloader fetches the set's candidate files from the userIcons tree (HTML error docs for nonexistent names are dropped as placeholders) and cleans stale cached names, and the icon map lists the provider family's state files (per the set's deviceType) with a default that exists — the base for single-icon sets, the off state for binary/multilevel — so the viewer switches states for a custom icon like any other set. Placeholder state files (the generic gray box the HC3 serves for states with no artwork, even under the requested extension) are dropped rather than cached, and the icon channel falls back to the cached sibling extension (png ↔ svg) on a miss; the viewer falls back to the set's default art for states with no artwork at all. The sim serves the cache to the viewer at GET /flua/icons/<set>/<file>; uncached icons 404 until the tool runs once. The viewer renders each QA's deviceIcon (both in the panel and on the condensed card, via the GET /flua/iconMap id→set lookup) and switches state files live: the value property picks the nearest ladder step (binary 0/100, multilevel 0..100 in tens), and a state string matches named state files (Opening, alarm, …). Unmapped or uncached ids fall back to the set's default file or no icon. Later, user-uploaded QA icons land in the same store.

A QA can preview a local icon set without touching the HC3: --%%icons:path/to/folder (resolved against the QA file, like --%%file) points at a folder holding the icons in the upload naming — icon.png, icon0.png+icon100.png, icon0..100.png, iconOpening.png, … The QA's own id becomes its deviceIcon (an explicit --%%property:deviceIcon wins), the icon map registers a synthetic Local<qaId> set listing whatever the folder holds, and the icon channel serves those files — the viewer switches them per value/state exactly like a cached set. Purely a preview: the folder never travels into .fqa packages, and the injected id does not render on a real HC3 (replace it with the uploaded set's User<id> id for production).

A browser-based icon manager (flua --tool icons ui) lists the controller's user icon sets — devices, rooms and scenes, each on its own tab — with live previews, uploads new sets (device icons per the chosen type's provider files; room/scene icons as a single PNG — 128×128 or larger), and deletes sets. The local server proxies every HC3 call with the .env chain credentials, so the browser only ever talks to localhost — no CORS, no credentials in the page.

Online (an HC3 backend), GET /flua/iconMap merges the live icon library into the checked-in catalog — custom User<id> sets and newer-firmware ids map too, so a QA running against the controller that owns its custom icon renders it in the viewer (after --tool icons download caches the art). Offline the map stays the checked-in catalog, and a QA that sets an unknown deviceIcon gets a one-time warning.

A download names every file <QA-name>_<file>_<id>.lua (the QA name is sanitized for the file system) — My QA_main_123.lua for the main, My_QA_lib_123.lua for extras — so several QAs can live in one directory without colliding, and the HC3 id travels with the files. The generated main regenerates the QA's header from the package: its UI comes back as --%%u rows (translated from uiView/viewLayout/uiCallbacks), variables as --%%var lines — and any old --%% directives in the downloaded code are dropped, since they may be outdated. uploadQA then takes either the QA name (it finds the project in the current directory) or the fully qualified <QA-name>_main_<id>.lua and updates that QA on the HC3; a plain <QA-name>_main.lua (from unpack) or a ready .fqa uploads as a new QA.

downloadQA also stamps every unpacked file with two metadata directives — --%%deviceId:123 (the HC3 device id) and --%%qaFile:lib (the QA file name the file maps to). uploadFile reads them, so one file can be pushed back to its QA without re-uploading the whole project — the VS Code task "Flua: Upload file to HC3" (installed by --tool setup) runs it on the file you are editing (${file}). Files downloaded before the directives existed still work: the <QA-name>_<file>_<id>.lua file name is the fallback. Updating the main file restarts the QA on the HC3; the tool warns when the target QA's name no longer matches the file name (a file copied out of another QA's project).

The HC3's export omits the identity properties (manufacturer, model, buildNumber, deviceRole, quickAppUuid), so downloadQA/downloadFQA restore them from the live device — the downloaded project/package keeps them. They only travel in a flua package when the project declares them (never the catalog skeleton's defaults), and updateQA syncs them to the HC3 like the other standard properties.

The tools need HC3 credentials (the .env chain, like online mode). uploadQA prints the new device id; updateQA puts all files at once; downloadQA writes a <QA-name>_main_<id>.lua main with the QA's directives plus the extra files — a normal flua project.

Static checks

.venv/bin/flua --check script.lua

Checks syntax, unknown --%% directives (typos), and deprecated API calls. It also warns when a v2 UI element (tabView/collapsible) is declared without --%%useUiView:true — on the real HC3 those render only from the uiView format, so the packaged legacy view would come out blank. Warnings don't fail the run; syntax errors exit 1. Good in CI. It checks the whole project: the main file plus every --%%file include (a missing include is an error, and $name entries resolve to flua's bundled libraries). --check --json prints the findings as one JSON document ({"ok", "findings": [{file, severity, message, line?, column?}]} — the 1-based line/column anchor each finding in the source, for editor diagnostics) instead of prose — the agent/CI form.

A wrong --%%type is an error with directions: it names close matches (typos) and points at flua --tool catalog, which lists every device type the sim supports (--json for a JSON array). flua --tool typeinfo <type-or-interface> is the deeper answer: the type's properties (with types, defaults and enums), its interfaces, and the actions a QA of that type should implement as QuickApp:<name> methods — each entry tagged with where it comes from (the type, a base type, or an interface). Action signatures render as name(a, b) — argc counts the implicit self, so an action takes argc - 1 arguments, named (with types) where the schema or the hand-maintained devices/action_overrides.json knows them, else a, b, c, ... placeholders.

Self-testing a QA (no repo needed)

A QA can be its own test suite — no pytest, no repo. Assert inside the QA, exit with the failure count, and let the caller (a shell, CI, or a coding agent) check the exit code:

.venv/bin/flua --api local examples/selfTest.lua   # prints PASS/FAIL lines
echo $?                                           # 0 = pass, non-zero = fail

Instead of hand-rolling the assertions, require("flua-test") — a built-in assertions library (no files needed, nothing travels in the .fqa):

local Test = require("flua-test")
local t = Test.new()
t:expect(cond, "msg")          -- PASS:/FAIL: line, counts failures
t:assert_eq(got, want, "msg")  -- deep compare, tables included
t:assert_json(text, "msg")     -- json.decode succeeds
t:finish()                     -- "failures: N" + exit(failures > 0 and 1 or 0)

Asserts can also TRAVEL to a real HC3 — declare the library as a QA file and the same code needs no editing: on the controller every assertion becomes a no-op (no printing, no counting, finish() returns 0), because the module detects the HC3 by the absence of flua's _FLUA global. In flua the shipped copy is the full library either way:

--%%file:$flua-test.lua,flua_test   -- ships in the .fqa; loads before main
local Test = require("flua-test")   -- works on the HC3 too (the file
                                    -- registers itself in package.preload)
-- ...or the shared-file idiom, no require: local t = fluaTest.new()

The exit code is the contract: an uncaught Lua error exits 1, and exit(N) (os.exit(N)) exits N — the QA must end with an explicit exit, or the run never finishes. A failing QA in a multi-QA run fails the process (the last failing QA's code wins), and flua prints a verdict line on stderr — flua: QA <name> (<id>) exited with code N — so agents can attribute the exit code.

flua test runs a whole suite of self-asserting test QAs at once:

.venv/bin/flua test                       # every *_test.lua under the cwd
.venv/bin/flua test tests/                # a directory (recursive)
.venv/bin/flua test qa_test.lua           # explicit files, any name
.venv/bin/flua test --list                # show what would run
.venv/bin/flua test --timeout 10 -v       # 10s per file; verbose failures
.venv/bin/flua test --json                # one JSON document: per-file status,
                                          # failures, assertion totals and output,
                                          # plus file and assertion summaries — the
                                          # VS Code Test Explorer contract

Each file runs in its own flua process — a test that never exits hits the per-file wall-clock timeout (reported as TIME, with the hint to end tests with t:finish()/exit(...)) instead of blocking the rest. The runner reports one PASS/FAIL/TIME line per file plus a summary and exits 0 only when everything passes: FAIL bad_test.lua (failures: 1), 1 passed, 1 failed, 0 timed out.

flua doctor

One command answers "why doesn't it work":

.venv/bin/flua doctor               # runtime, venv, HC3 credentials +
                                    # reachability, LuaLS/.vscode setup,
                                    # extension, flua-mcp, project files
.venv/bin/flua doctor --no-network  # skip the HC3 ping
.venv/bin/flua doctor --json        # machine-readable checks for agents

It reports one ✓/✗ line per check and exits non-zero when any check fails — paste the block into a support question instead of describing the setup. Secrets never appear: credentials are reported as set/unset with their source file, never as values.

For machine-readable runs (agents parsing the log), --log json emits one JSON object per line — {time, level, tag, qaid, msg} — with stdout kept pure JSON and flua's own notices on stderr; --logfile FILE writes a copy of the log (ANSI stripped, JSON lines with --log json). --syslog FILE appends every structured system/crash event as one JSON line — the complete history, where GET /flua/systemLog is the bounded in-memory buffer.

--trace LIST adds opt-in run traces to the same channel (comma list of api, ui, net, timer, or all) — one {"event": "trace", "data": {"category": …}} line per: api — every api.* call a QA makes (method, URL, status, and the request body — the arguments that usually go wrong); ui — incoming device actions and callUIEvent interactions; net — HTTP/TCP/UDP/WS/MQTT operations and results (sizes, not payloads); timer — timer starts and expiries. It is the same history an agent reads with --syslog, so a single file gives both the lifecycle and the QA's behavior. Bodies are truncated at 1000 chars (they may carry secrets). Both have --%% directive forms — --%%trace:api,ui and --%%syslog:run.json — so a run's tracing can live in the QA header, an --%%include file, or .flua-directives (the CLI flags win over them).

MCP server (flua-mcp)

The same surface is available as an MCP server for hosts that prefer one (Claude Desktop, Copilot, …). It ships with flua:

flua-mcp                  # stdio JSON-RPC (dual-era: 2026-07-28 modern, 2025-06-18 legacy)
flua-mcp --version

Both qa_run and qa_start take a trace parameter (api/ui/net/timer, all): qa_run returns the trace lines in its trace field, and a traced session feeds them through qa_probe's systemEvents (the same --trace stream). Resources: the docs ship in the wheel and are served as flua://docs/* (e.g. flua://docs/USAGE.md, flua://docs/tutorial/…) via resources/list/resources/read, with docs_list/docs_read tools for hosts without resource support — an agent host can read the flua docs without a repo checkout. Prompts: qa_debug (seeded debugging guidance) and qa_skeleton (a runnable self-testing QA template). Host registration: add flua-mcp as a stdio server in your host's MCP config — no extra install, no extra dependencies. The full reference (protocol surface, tool schemas, error semantics, examples): docs/mcp.md.

UI behavior folds into the same loop from Lua: _FLUA.uiEvent(element, eventType[, value]) injects a UI event exactly as the HC3 UI would deliver it (values arrive as strings, like the real UI), and self:getView() returns the current rendered view — updateView changes included. A text rendering of the UI without a browser: flua --tool ui script.lua; the structured form flua --tool ui --json script.lua returns {name, type, useUiView, elements, callbacks} — the agent form, no prose to parse.

flua --tool ui --device ID runs the same rendering on an HC3 device — the use case is the proxy: with --%%mode:proxy,noUI you edit the proxy's UI in the HC3's own editor, then fetch it back as --%%u rows (plus the raw UI JSON — the shorthand is lossy, unknown component kinds degrade to labels) and adopt what you want into the QA.

When the logic under test needs external interactions, serve the sim API with --ui PORT and drive it over HTTP (/plugins/callUIEvent, /devices/<id>/action/<name>, /devices/<id> for state), and keep timer logic deterministic with --start, --speed, --instant, and --seed. The quickapp-test skill installed by --tool setup documents the whole loop for coding agents.

Every console line lands in the sim's GET /debugMessages buffer (the HC3's console log, served over REST): QA lines with their tag, flua's own notices under the flua tag, and runtime-level lines untagged. last/offset/filter/types query params, DELETE /debugMessages clears it, GET /debugMessages/tags lists the QA tags seen — a machine-readable log feed with the same surface the real HC3 offers.

Registered endpoints (api.registerEndpoint)

Emulate a missing HC3 endpoint from Lua — modules can bring whole panels alive in the offline sim (examples/mock-panels.lua is one, required from examples/uses-mock-panels.lua):

api.registerEndpoint("GET", "/panels/sprinklers/{id}", function(req)
  return { id = tonumber(req.params.id) }, 200   -- (data, status)
end)
  • Built-in routes always win over normal routes; a registered route answers ANY QA's api.* calls when nothing built-in matches, before the 404/remote fallback. A QA's own routes are consulted first, then every other QA's in registration order — a mock-panel QA deployed in the same run (with its own UI and device) answers other QAs' calls.
  • override=true inverts that: an override route REPLACES the built-in's behavior — the pattern for prototyping panel logic in Lua (delayed state transitions via setTimeout, events via _FLUA.postRefreshEvent) before promoting it to a Python built-in once the contract is understood. examples/alarm-logic.lua (the module) + examples/alarm-panel.lua (deployed as a QA with arm/disarm UI) + examples/uses-alarm-panel.lua (a consumer QA) demonstrate the whole loop. Precedence: override (any QA's) > built-in > normal registered (any QA's) > 404/remote; among several matches, the earliest registration wins.
  • req = {method, path, params, query, body} — {name} segments become string params, the query arrives parsed, the body as sent.
  • The handler runs as a QA callback on the pump: the full api surface works inside it (including _FLUA.postRefreshEvent). A handler crash completes the call with 500; a handler calling its own endpoint gets 404 (no recursion).
  • Routes die with the QA — exit/restart clears them; a restart's onInit re-registers.
  • Offline-sim feature: in remote mode the real HC3 owns the house and registered routes never apply.

flua extensions (_FLUA)

Everything HC3-compatible is a plain global (QuickApp, fibaro, api, net, mqtt, json, …) — and like on the HC3 (one Lua state per QA), a QA's _G is its own environment: _G.x = 1 writes the QA's global x, invisible to other QAs and the shared runtime. flua-specific helpers live on _FLUA so your code stays portable:

  • _FLUA.qaId — this QA's id; _FLUA.config — this QA's config table
  • _FLUA.mode — this QA's effective runtime mode: "offline", "online" or "proxy" (vs config.mode/config.offline/config.proxy, which are the directives the QA declared — a QA can pin itself offline in an online run)
  • _FLUA.arg — the file path / -e marker
  • _FLUA.mainPath — the main QA file's directory with a trailing separator: io.open(_FLUA.mainPath .. "data.json", "r") reads files shipped next to the QA regardless of the cwd (absolute when loaded via the CLI; the unpack directory for .fqa packages)
  • _FLUA.hostIP — the dev machine's LAN address (the laptop running flua) — for QAs that call back to services on the host (mock servers, tooling); 127.0.0.1 when no interface is reachable
  • _FLUA.exit(code) — stop the engine (vs exit(code) / os.exit() in a QA, which stop only that QA — os.exit() is the name real HC3 QAs use)
  • _FLUA.keepAlive() — keep this QA (and with it the run) alive past idle, like --%%keep-alive:true but at runtime and in every mode; the QA's exit clears it. The bundled sim devices call it in onInit (no setInterval hack needed)
  • _FLUA.qa(id) — another QA's QuickApp instance (lupa proxy)
  • _FLUA.loadFile(path) — load a Lua file and return a chunk bound to this QA's environment (fibaro/api/net visible inside): the sanctioned runtime loader for harness and test code; dofile does the same implicitly, load/loadfile need the QA's _G passed explicitly
  • _FLUA.loadQAfromFile(path, directives?) / _FLUA.loadQAfromString(code, directives?) — dynamic QA loading; directives is an optional table of directive strings added to the loaded QA's config
  • _FLUA.loadFQAfromFile(path, directives?) — like loadQAfromFile for a .fqa package: unpacks it to a temp dir first (the CLI's pipeline), name/type/UI come from the package header
  • _FLUA.loadSimDevice(name, directives?) — load a simulated device bundled with flua (src/flua/simdevices, shipped in the wheel): the file name without suffix (.lua then .fqa), e.g. "temperatureSensor". The optional directives table overrides the device's --%% header like loadQAfromFile's (rename, preset properties). Returns the device id, or throws an error naming the bundled set
  • _FLUA.async.run(fn) / _FLUA.async.await(worker) / _FLUA.async.wait(ms) — coroutine awaits
  • _FLUA.millitime() — virtual time in whole milliseconds (sub-second timing; os.time() is whole seconds, os.clock() is real CPU time)
  • _FLUA.postRefreshEvent(event) — inject a fake refreshStates event (alarm, weather, device property change, …) to debug reactive QAs: it lands in the sim feed (api.get('/refreshStates')) and reaches every RefreshStateSubscriber; a DevicePropertyUpdatedEvent also updates the shadowed device. created/sourceType are filled in when omitted.
  • _FLUA.uiEvent(elementName, eventType[, value]) — inject a UI event exactly as the HC3 UI delivers it (the same route the viewer uses), returns (data, status); the QA's callback fires async, values arrive as strings. The verify loop's browser-free UI testing (with self:getView() to read the rendered view).
  • _FLUA.setTimeout(fn, ms, qaId) — timer with explicit QA attribution
  • _FLUA.background(fn) — tag a callback as housekeeping: its timers fire while the run lives but never keep it alive (the pending-work check skips them), so a run drains when the real work is done — the escape hatch for keep-alive loops like EventRunner's midnight scheduler. Compose inline: setTimeout(_FLUA.background(loop), ms); a QA whose only work is tagged exits immediately. Returns fn.
