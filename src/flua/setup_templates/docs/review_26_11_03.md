# flua project review — 2026-11-03

## Executive summary

flua is a capable, unusually well-documented development environment for
Fibaro QuickApps. Its strongest design choice is not the breadth of its
emulation, but the clear execution contract underneath it: a single Lua-entry
pump, message-based Python/Lua communication, per-QA isolation, virtual time,
and explicit offline/online/proxy modes. The offline-first default is both a
good safety boundary and a strong fit for fast iteration.

The project also takes the user journey seriously. A beginner can move from
installing the tool to building, testing, and deploying a QuickApp, while
experienced developers get a CLI, VS Code integration, REST simulation,
network libraries, and an agent-facing MCP interface.

The main risks are now about **managing the size of the product**: core
orchestration is concentrated in large modules; runtime and compatibility
details are not presented as one easy-to-verify matrix; and the simulator's
deliberate partial parity is easier to discover in reference material than at
the point where a user first encounters it. These are manageable risks, not
reasons to redesign the architecture.

## At a glance

| Area | Assessment |
|---|---|
| Runtime architecture | Strong principles and clear behavioral contracts |
| Offline development and safety | Excellent; offline is the default and online is opt-in |
| QuickApp onboarding | Strong, especially the step-by-step tutorial |
| Testing and packaging discipline | Strong automated coverage and a useful wheel smoke test |
| HC3 parity transparency | Honest reference material, but the limits could be more visible in the workflow |
| Maintainability | Good modular boundaries in some areas; too much responsibility still sits in `engine.py` |
| Compatibility communication | Needs a single, current statement of the supported Python/Lua/runtime combinations |

## What is working well

### 1. A coherent execution model

The single-entry rule—Lua is entered only by the pump—keeps the Python/Lua
boundary understandable and avoids a class of reentrancy problems. Messages
cross the boundary as data rather than function references, and the docs
explain how timers, callbacks, network work, and remote API calls fit into
that model. Per-QA coroutine suspension also means that one QA waiting for
sleep or a remote call does not have to stop every other QA.

The architecture is supported by explicit contracts rather than relying only
on comments: [ARCHITECTURE.md](../ARCHITECTURE.md),
[docs/concurrency.md](./concurrency.md), and
[docs/invariants.md](./invariants.md) describe the rules and point to tests
that pin important behavior. This is a strong foundation for making changes
without silently breaking timing, event ordering, or identity semantics.

### 2. Offline-first is a good product and safety decision

A fresh run uses the simulated HC3; accessing a real controller requires an
explicit online choice. That makes experimentation safe by default and
avoids surprising network access when credentials happen to be present.
Proxy mode adds a useful third option for cases where the actual HC3 UI or
controller behavior matters.

The distinct ID namespaces and explicit routing rules are also practical:
developers can reason about which devices are local and which calls may be
forwarded. The decision is documented in
[docs/decisions/0001-default-mode-is-offline.md](./decisions/0001-default-mode-is-offline.md)
and covered by tests.

### 3. A notably complete QuickApp learning path

The [tutorial](./tutorial/README.md) is a real strength. It starts without
assuming programming experience, builds one example through successive
chapters, introduces the viewer and virtual clock, and eventually reaches
testing and deployment. The main [USAGE.md](../USAGE.md) then serves as the
broader reference for users who already know what they need.

The development loop is also thoughtfully supported: project setup,
Lua-language-server metadata, VS Code run/debug configurations, `flua doctor`,
static checks, virtual-time controls, a UI viewer, self-testing QuickApps,
and upload/download tools all reduce the amount of surrounding setup a
developer must invent.

### 4. Good test and release safeguards

The checked-in suite contains hundreds of focused test cases and uses local
mock HC3 servers rather than requiring a live controller. CI runs Ruff and
the offline suite across multiple Python versions. The wheel job installs the
built package in a clean environment and smoke-tests setup, QA creation, and
static checking—an important complement to source-tree tests.

This is especially valuable for a project that emulates a large external
surface: tests, invariants, endpoint documentation, and examples together
make compatibility decisions easier to inspect.

### 5. A useful breadth of workflows without a large runtime dependency tree

The project supports offline runs, online rehearsal, proxy operation,
multi-file QAs, simulated devices, REST access, HTTP/TCP/UDP/WebSocket/MQTT,
record/replay, and MCP-based agent workflows. That is a substantial
development environment, yet the runtime dependency footprint remains small.
The [README](../README.md), [MCP guide](./mcp.md), and
[REST endpoint reference](./rest-endpoints.md) make these distinct surfaces
reasonably discoverable.

## Areas to improve

### 1. Core orchestration has become concentrated

`src/flua/engine.py` is about 2,800 lines and owns or coordinates a wide range
of responsibilities: QA lifecycle and file operations, logging and event
feeds, the pump and message handlers, HC3 polling, proxy connections, network
operations, and persistence. `cli.py` and `config.py` are also substantial.
The central engine is a natural coordination point, but the number of
responsibilities increases the cost of understanding a change and raises the
risk that unrelated paths become coupled.

**Recommendation — medium-term:** keep `LuaEngine` as the stable facade and
preserve the current message and lifecycle contracts, but move cohesive
subsystems behind small collaborators as changes naturally touch them.
Reasonable seams include transport handlers, proxy/HC3 polling, QA
file/package operations, and persistence. Do not split solely to reduce line
count; each extracted boundary should have a clear owner and focused tests.

### 2. Runtime compatibility is not stated in one authoritative place

The supported Python range in `pyproject.toml` and the CI matrix do not quite
match: package metadata includes Python 3.13, while the test matrix covers
3.11, 3.12, 3.14, and 3.15. The same manifest pins `lupa` to 2.6 and notes
that it bundles Lua 5.4, while also referring to development/testing against
Lua 5.5. The language-server configuration documents Lua 5.4, and several
tutorial and README transcripts show Lua 5.5 and much older flua versions.
Some of these differences may be intentional, but a new user cannot readily
tell which runtime is installed, which is tested, and which is the intended
HC3 compatibility target.

**Recommendation — high priority:** publish one compatibility table that
distinguishes Python versions, packaged Lua version, development/test Lua
version, and HC3 target assumptions. Add Python 3.13 to CI or remove it from
the stated support range. Use generic version placeholders in tutorial
transcripts, or refresh them as part of releases. Relevant sources are
[pyproject.toml](../pyproject.toml),
[the CI workflow](../.github/workflows/tests.yml), and
[USAGE.md](../USAGE.md).

### 3. The simulator's intentional limits should be closer to the user

The project is appropriately candid that the simulated REST API is a useful
subset, not a complete controller. The endpoint guide separates
state-backed routes from shape-only stubs, and the runtime exposes a
capability surface. However, an HC3-shaped response with empty data can look
plausible to a developer whose QA expects real controller state. A user may
discover the limit only after debugging the behavior of their QA.

**Recommendation — high priority:** make the implemented/partial/unsupported
surface prominent in the first-run and offline-simulation workflow, not only
in the reference docs. Link `flua --capabilities-json` and
[docs/rest-endpoints.md](./rest-endpoints.md) directly from the relevant
simulation guidance. Where practical, make capability output identify
shape-only stubs so users can distinguish “supported but empty” from
“simulated with real state.”

### 4. The documentation set is strong but large and duplicated by purpose

There are several useful entry points—README, USAGE, the tutorial,
architecture/concurrency references, VS Code setup material, and packaged
documentation for MCP. That breadth is appropriate for the product, but
users can still be unsure which document is the next one to read. The main
user guide is long, while some concepts and setup steps also appear in the
tutorial and README. The packaged docs are synchronized by a script, which
helps, but remains another consistency boundary.

**Recommendation — medium priority:** retain the detailed manual and
tutorial, but make the landing page task-oriented: “new to QuickApps,”
“already have a QA,” “debugging,” “testing,” and “deploying.” Keep canonical
explanations in one place and link to them from the other surfaces. Add a
small CI check for especially drift-prone examples or compatibility values.

### 5. Cross-platform support deserves a visible install-validation story

The package is presented as cross-platform and supports a broad Python
version range. The regular test matrix runs on Ubuntu, and the clean wheel
smoke test also runs on Ubuntu. The project already documents that `lupa`
wheels are not available for every interpreter/platform combination and may
need a source build.

**Recommendation — medium priority:** either add periodic package-install
smoke tests on macOS and Windows or clearly document which combinations are
actively verified and when users may need a compiler to install `lupa`.
This is particularly useful for new users, for whom a native build failure
looks like a flua failure.

## Ease of use for QuickApp developers

For a developer with VS Code and basic terminal familiarity, flua offers a
strong loop: create a Lua file, run it offline, inspect logs or the browser
viewer, fast-forward time, add assertions, then deploy the same project.
The tutorial makes that path accessible to people new to QuickApps, and the
tools reduce common packaging and transfer chores.

The experience is less straightforward once work crosses the emulator/HC3
boundary. Users need to understand directives and mode precedence,
credentials, package files, what the simulator actually models, and which
calls are extensions versus HC3 behavior. Those topics are documented, but
they are a larger conceptual surface than the first “hello QA” suggests.
The most important improvement is not another feature; it is making the
runtime compatibility and simulation limits visible exactly when users
choose a workflow.

## Suggested order of work

1. **Clarify the supported runtime matrix** and align CI, package metadata,
   Lua-language-server settings, and example transcripts.
2. **Surface simulator coverage at point of use**, linking capability output
   and clearly identifying shape-only endpoints.
3. **Keep the engine modular as features evolve**, extracting tested
   subsystems at natural boundaries rather than undertaking a broad rewrite.
4. **Simplify the documentation entry points** and add low-cost checks for
   examples and duplicated compatibility claims.
5. **Add cross-platform install smoke coverage** or document the precise
   verified platform/interpreter combinations.

## Review scope

This is an architecture, documentation, testing-process, and user-experience
review—not a security audit or a full behavioral verification. No live HC3
was contacted and no test suite was run for this documentation-only task.
The worktree already contained uncommitted changes when reviewed; those
changes were not treated as settled project behavior or modified as part of
this review.
